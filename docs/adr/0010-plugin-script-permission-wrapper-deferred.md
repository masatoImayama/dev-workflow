# ADR 0010: プラグインスクリプトの許可集約ラッパー（issue #131）は観測不足のため実装を保留する

## ステータス

保留（Epic #174 / Task #131）。着地は「(C) 判断を保留し、観測項目を明確化して据え置く」。

## コンテキスト

issue #131 は、`sandbox-exec.sh` / `plan-waves.sh` / `merge-lane.sh` / `watchdog.sh` /
`count-skips.sh` など、dev-workflow が run 中に呼ぶ多数のプラグインスクリプトが、
狭い Bash 許可を運用しているチームでは**スクリプトごとに個別の完全一致許可エントリ**を
積み上げてしまう（issue #121 の実測: kikumemo-front での Epic 1本の run で約40件）ことを
問題として起票したものである。

issue #131 自身が着手の判断基準を明記している。

> Epic #122 で `README.md` の「YOLOモード / パーミッション設定」にスコープ指針が入る。
> その運用で許可エントリの増殖が実際に問題として残るかを、**1〜2 Epic 分の run で観測してから**
> 着手するのが妥当。**観測されなければ wontfix でよい。**

Epic #174 本文もこの判断基準をそのまま引き継ぎ、加えて (A) を選ぶ場合の必須事項として
次を明記している。

> **#131 は「ラッパー経由で任意コマンドが実行できると許可を1本に絞る意味が薄れる」という
> トレードオフを持つ**（`sandbox-exec.sh` はそもそも任意コマンドをコンテナへ投入する）。
> サブコマンド名のホワイトリストで限定すること

本タスクの目的は、まず**この判断基準に従って着手の要否を判定すること**であり、
実装ありきで進めるものではない。

## 確認できたこと・確認できなかったこと（推測で実装しないため）

### 確認できたこと

1. **前提タスク #140 は完了済みである**（`de65d1a`）。#140 は generator/evaluator が生成する
   コマンドの「書き方」（`cd`+`git` の分離、ポーリングループ・env前置の禁止など）を承認プロンプトが
   出にくい形に統一したものであり、**dev-workflow が呼ぶ「異なるスクリプトの種類」を減らす
   変更ではない**。したがって #140 の完了は「集約すべき許可エントリの範囲」を狭めておらず、
   #131 が対象とする問題（スクリプトごとの完全一致エントリの積み上げ）はそのまま残っている。

2. **Epic #122（`core/references/harness-hygiene.md` および README「YOLOモード /
   パーミッション設定」節）は、YOLO 運用の推奨設定として `permissions.allow` に `Bash(*)` を
   置くことを明記している。** この推奨に従う運用では、個々のスクリプト呼び出しは
   既存の `Bash(*)` に包含されるため、そもそも新規の完全一致エントリが積まれる余地が無い。
   Epic #174 本文の「スコープ外」節も「README推奨の`Bash(*)`allow運用を必須にすることは
   変えない（#131は絞った許可の運用者向けの改善）」と明記しており、**#131 が解決対象とする
   実害は「推奨設定に従わず、より狭い許可を運用しているチーム」に限定される**ことが
   Epic 自身によって確定している。

3. **Epic #122 の README 反映（PR #136/#137）以降、dev-workflow 自身が2本の Epic
   （#143「faster-run」・#173「windows-lane-viability」）を完走し、外部の駆動先プロジェクト
   （pnpm + vitest構成、22タスク・5ウェーブ）でも1本の run が完走している
   （issue #138 の「環境」節に記載）。** これらの run から実際に観測された摩擦は、
   本 Epic の他タスク（#138 バックグラウンド実行での停止、#140 承認プロンプトの誘発、
   #141 codegen生成物の誤検知、#142 SKIP誤判定）としてそれぞれ個別に起票されている。
   **この期間中に issue #121 と同種の「許可エントリの増殖」を報告する新規issueは
   起票されていない。** 本プロジェクトは run 中に観測した摩擦を都度issue化する運用が
   実際に機能している（#138/#140/#141/#142 がその実例）ため、この不在は一定の意味を持つ
   観測結果である。

4. **README がすでに公開している許可記法（`permissions.deny`/`allow` の例）は、
   前方一致・後方一致・中間一致いずれのワイルドカード（`*`）もサポートしている
   ことが、README 自身の既存の記述例（`Bash(rm *)` / `Bash(* rm *)` / `Bash(*)`）から
   確認できる。** これは、狭い許可を運用するチームであっても、
   `Bash(bash "${CLAUDE_PLUGIN_ROOT}/scripts/*")` のような**1本の許可エントリ**を
   あらかじめ設定しておけば、dev-workflow の個々のスクリプト呼び出しがその1本に包含され、
   個別の完全一致エントリが積まれること自体を防げる可能性が高いことを示唆する。
   これが事実であれば、issue #131 が提案するラッパー実装（サブコマンド名のホワイトリスト・
   全呼び出し箇所の書き換え・Codex側の対応確認を伴う広い差分）を経由せず、
   **ドキュメント追記のみ**で同等の効果を得られる可能性がある。

### 確認できなかったこと

- **観測期間中（#122以降の3本のrun）に、狭い許可を運用しているチームが実際に含まれていたか
  どうか。** 上記3(#143/#173/外部run)がいずれも README 推奨の `Bash(*)` を採用済みだった場合、
  「新規issueが起票されなかった」という事実は #131 の対象読者（狭い許可の運用者）には
  何も語らない。dev-workflow自身の `.claude/settings.local.json` はgitignore対象のため
  履歴が残らず、過去のrunでどの許可設定が使われていたかを本タスクの範囲では復元できなかった
  （本worktreeで確認できたファイルは作成日時が直近1日以内であり、#122/#143/#173実行当時の
  状態を反映していない）。
- **上記4のワイルドカード許可エントリが、Claude Codeの「常に許可」自動追記の挙動を
  実際に抑止するかどうか。** README の既存記法から論理的に導けるが、本タスクでは
  実機でのプロンプト再現・検証は行っていない。
- **Codex側の `.codex/rules/*.rules`（`codex execpolicy`）が、同種のディレクトリ単位の
  集約（1ルールで `scripts/` 配下の呼び出し全体をカバーすること）をサポートするかどうか。**
  `docs/dev-workflow-multi-vendor-guide.md` はClaude Codeの`permissions`とCodexの
  `execpolicy`が別機構であることを実測で確認済みだが、execpolicyのルール記法の詳細
  （ディレクトリ単位のワイルドカード可否）までは本タスクの範囲では確認できなかった。
  issue #131 自身が検討事項として挙げている3点目がそのまま未解決で残る。

## 決定

**issue #131 が提案するラッパー（`scripts/dw`）の実装は、本タスクでは行わない（保留する）。**
issue #131・Epic #174 いずれも判断基準として「1〜2 Epic 分の run で問題が観測されなければ
wontfixでよい」としているが、上記のとおり本タスクでは

- 観測期間中に問題の再発が報告されていない（一定の消極的根拠にはなる）一方で
- その観測期間に「狭い許可を運用するチーム」が実際に含まれていたかを確認できておらず
- ラッパーより遥かに低コスト・低リスクな代替（ワイルドカード許可1本のドキュメント化）が
  未検証のまま存在する

という状況にあり、**「wontfixで確定する」「今すぐラッパーを実装する」のいずれも
推測に基づく判断になる**（Epic #174 完了基準6に反する）。そのため今回は
**判断を保留し、次に何を観測すればどちらに転ぶかを明確にした状態で issue を open のまま残す。**

コード変更・README変更は行わない。ADRのみを追加する。

## 理由

- issue #131 の提案自体が「サブコマンド名のホワイトリストで任意コマンド実行を防ぐ」
  「既存呼び出し箇所を全面的に書き換える」「Codex側の対応を確認する」という3点の
  検討事項を伴う、差分の広い変更である。観測不足のままこれを実装すると、
  後から「そもそも狭い許可の運用者は観測期間中に存在しなかった」
  「ワイルドカード許可1本で十分だった」のいずれが判明しても手戻りになる。
- 一方で「観測されなかったからwontfix」と断定するには、観測対象母集団
  （狭い許可を運用しているチームの実行回数）が本タスクの範囲では確認できず、
  絶対不在の確証にならない。
- ADR-0009（flaky suite対策の保留）と同型の状況であり、同じ理由づけの型
  （前提が確認できるまでは実装も wontfix 確定もしない）を踏襲する。

## 再開条件

次のいずれかが観測された時点で、本 ADR を更新するか issue #131 を再検討する。

1. **狭い許可運用のまま許可エントリ増殖の再発が報告された場合**（issue #121 と同種の
   実測付き報告）: まず下記2のワイルドカード許可1本での緩和を先に試す価値があるかを
   判定したうえで、それでも不十分なら issue #131 のラッパー実装（(A)）に進む。
2. **ワイルドカード許可1本（`Bash(bash "${CLAUDE_PLUGIN_ROOT}/scripts/*")` 相当）による
   緩和が実機で有効/無効いずれかに確定した場合**: 有効であればREADMEへの記載のみで
   issue #131 をクローズできる可能性が高い。無効であればラッパー実装の必要性が高まる。
3. **Codex側の `execpolicy` がディレクトリ単位の集約をサポートするかどうかが確認できた場合**:
   非対応であれば、たとえClaude側でラッパー/ワイルドカードのいずれかを採用しても
   Codex側は個別ルールの積み上げが残ることになり、issue #131 の解決範囲を
   「Claude Codeのみ」と明記する必要が生じる。

いずれの観測も、次のEpicで実際に狭い許可運用のチームに対してrunを実行する機会がない限り
得られない可能性が高い。その場合は再開条件1〜3を明示的な観測タスクとして
別issueに切り出すことも検討してよい。

## トレードオフ

- issue #131 が解決しようとしている実害（狭い許可運用チームでの許可エントリ増殖）は、
  本タスクでは未解決のまま残る。該当するチームが実在すれば、今後も同じ摩擦が継続する。
- 判断を保留したことで、issue #131 は再びオープンなタスクとして残り続ける。
  再開条件（上記）が観測されるまで、次のEpicでも「前提未確認のため保留」を
  繰り返す可能性がある。

## 却下した代案

### 観測不足を無視してラッパーを実装する（(A) を選ぶ）

issue #131・Epic #174 いずれも「まず観測してから」という手順を明示しており、
その観測（狭い許可運用チームでの再発有無）が本タスクの範囲では確認できていない。
確認できていない前提の上に広い差分（サブコマンドホワイトリスト・全呼び出し箇所の
書き換え・Codex側の検証）を積むと、後から前提が反証された場合に手戻りが大きい。

### 観測されなかったことをもってwontfixとして完全クローズする（(B) を選ぶ）

「新規issueが起票されなかった」という消極的事実だけでは、観測対象母集団
（狭い許可運用チームの実行回数）が本タスクの範囲でゼロだったのか、
実際に運用されていて問題が起きなかったのかを区別できない。前者であれば
「観測できていない」が正しい記述であり、「問題が無いと確認できた」と書くのは
Epic #174 完了基準6（推測で実装しない）に反する。
