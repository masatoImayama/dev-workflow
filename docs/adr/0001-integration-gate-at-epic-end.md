# ADR 0001: 統合ゲート（フルスイート実行）を Epic 末の1回に集約する

## ステータス

承認済み（Epic #143 / Task #144）

## コンテキスト

run は1つの Epic に4〜5時間かかっており、直列区間の削減が Epic #143 の目的である。
従来、**ウェーブごとに wave ブランチ上でプロジェクトの全テスト（フルスイート）**を走らせて
いた（Claude 版 `skills/run/SKILL.md` Step 6、Codex 版 `adapters/codex/run-loop.sh` の
`mechanical_gate()`。Codex は `lanes=1` 固定のため、実質「タスクごと」に全テストを実行していた）。

この結果、`ウェーブ数 × フルスイート時間` がそのまま直列区間になっていた。ウェーブ数が多い
Epic ほど、この待ち時間が実行時間全体を支配する。

## 決定

フルスイートの実行を**ウェーブごとから Epic につき1回（全ウェーブ完了後、Epic 一括レビューの
前）に集約する。** 機械的ゲートを次の三段構成に変更する。

| 検証点 | 対象ツリー | 実行するもの | 頻度 |
|---|---|---|---|
| レーン内ゲート | generator の isolation worktree | 変更範囲のテスト | タスクごと（変更なし） |
| ウェーブ末の取り込み検証 | wave ブランチ | merge-base 完全一致検証（`merge-lane.sh`）＋可読性ガード（`check-readability.sh --git`） | ウェーブごと |
| **Epic 統合ゲート**（新設） | Epic ブランチ | **プロジェクトの全テスト＋可読性ガード** | **Epic につき1回**（全ウェーブ完了後） |

- merge-base 完全一致検証・exit 10/11 の差し戻し・cherry-pick 禁止・wave ブランチを origin へ
  push しない・Epic ブランチへ `--ff-only` で進める・Epic ブランチへ force push しない、という
  既存の安全策はすべて維持する。**削るのはフルスイートの実行頻度だけである**
- 「回帰なし」を宣言できるのは Epic 統合ゲートだけになる。generator が自分の報告に「回帰なし」
  と書かない既存規定（`core/roles/generator.md`）はそのまま維持する
- Epic 統合ゲート失敗時は、Epic ブランチが既にウェーブを取り込み済みのため「Epic ブランチは
  無傷」を前提にできない。失敗内容を Epic issue にコメントし、修正タスクとして issue 化して
  通常のウェーブループで対応させ、Epic 統合ゲートを再実行する。**再試行は最大2回。** それでも
  通らなければ run を止めずに PR を作成し、PR 本文冒頭に「Epic 統合ゲート不合格」と明記して
  人間へ渡す
- 原因ウェーブの特定は、Epic ブランチ上の各ウェーブ取り込みコミット（`wave/${EPIC_NUM}/N` の
  tip）を古い方から順に checkout してフルスイートを再実行する、ウェーブ単位の二分探索で行う
  （`skills/run/references/recovery.md`「Epic統合ゲート失敗時の原因特定手順」）

## 理由

- ウェーブ数に比例していた待ち時間を Epic につき1回に固定できる。ウェーブ数が多いほど削減効果が
  大きい
- レーン内ゲート・ウェーブ末の取り込み検証（merge-base 完全一致検証・可読性ガード）は
  そのまま維持されるため、**構造的な安全網（マージ健全性・可読性）は失われない**
- 可読性ガードは Docker 不要で高速なため、ウェーブ末に残す。Epic 末へ移すのは低速な
  フルスイートだけに限定する

## トレードオフ（意識的な選択として受け入れるもの）

- **回帰の検知が Epic 末まで遅れる。** あるウェーブが持ち込んだ回帰は、次のウェーブ以降、
  最終的には Epic 統合ゲートまで顕在化しない
- **ウェーブ内の自動の安全網は、レーン内ゲート・マージ健全性チェック（merge-base 完全一致
  検証）・可読性ガードだけになる。** フルスイートによる安全網はウェーブ単位では失われる
- **Epic ブランチに「フルスイート未通過のコミット」が一時的に載りうる。** 従来の不変条件
  「Epic ブランチには統合ゲートを通ったコミットだけが載る」は変わる
- これは実行時間短縮のための意識的な選択であり、**main への取り込みは常に人間の PR レビューを
  通ること**、および **Epic 統合ゲート自体は Epic につき1回必ず実行されること**が前提である

## 却下した代案

### 代案A: ウェーブごとのフルスイートを維持し、ウェーブの並列度を上げて相殺する

並列度（レーン数）を上げても、ウェーブごとのフルスイート自体の所要時間（1回あたり）は
変わらないため、`ウェーブ数 × フルスイート時間` という直列区間の構造は解消されない。
並列化（Epic #143 の他タスク #15・#16・#18・#20〜#22）とは独立に効く削減策が必要だった。

### 代案B: フルスイートを間引く（例: 3ウェーブに1回）

「何回に1回」という間引き基準が恣意的になり、回帰の検知タイミングが不規則になる。
Epic 末の1回に完全に寄せる方が、`何を実行すれば「回帰なし」と言えるか`という基準を
単純に保てる（「Epic につき必ず1回」という不変条件のほうが、部分的な間引きより検証しやすい）。

### 代案C: ウェーブ末の取り込み検証も完全に省略し、Epic 統合ゲートだけに一本化する

merge-base 完全一致検証（ベース逸脱の検出）と可読性ガードは高速であり、これらまで
Epic 末に先送りすると、ベース逸脱やレビュー不能な可読性違反がウェーブをまたいで積み上がり、
原因特定の対象範囲が広がってしまう。**安価に検証できるものは早期に、高価なものだけを
後段に集約する**という原則に基づき、ウェーブ末の取り込み検証は維持することにした。

### Codex（`lanes=1` 固定）を Claude 版と別方針にする案

Codex はサブエージェント専用 worktree を持たないため `lanes=1` 固定で動作するが、
「ウェーブの概念・merge-base 検証・wave ブランチ経由の統合」という設計は Claude 版と
共通仕様として適用されている（`core/instructions.md`「Codex の位置づけ」）。Epic 統合ゲートの
考え方だけを Codex で例外扱いにすると、アダプタ間に機能差が生まれ、運用手順が CLI ごとに
変わってしまう。**アダプタ間に機能差を作らない**という既存方針（watchdog の`--abort`等と
同じ）に従い、Codex 側（`adapters/codex/run-loop.sh` / `skills-codex/dev-workflow-run/SKILL.md`）
にも同じ三段構成を適用した。
