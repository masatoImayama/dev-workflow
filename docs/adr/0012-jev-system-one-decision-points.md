# ADR 0012: Jev（System One Model）は任意依存として ①② にのみ結線する（③ は計測で効果を否定し結線しない）

## ステータス

承認済み・①② は実測で採用・③ は実測で効果を否定し結線せず（issue #244）

## コンテキスト

issue #244 は、TypeSafe AI が 2026-09-15 に公開した **Jev**（System One Model。文章を生成せず
`Choice` / `Score` / `Noul` の型付きの判断だけを返すモデル）を、ハーネスの判断点に組み込めるか
棚卸しした。適合条件は3つ。

1. 局所的な文脈で閉じる（`state` + 最長の question で 32k トークンに収まる）
2. 選択肢が有限
3. **間違えても成果物が壊れない**（安全側への倒し方が定義できる）

棚卸しの結果、◎ 2件・○ 1件・△ 2件・✕ 4件に分類された。本 ADR は ◎○ の3件（①②③）を
**shadow mode で実測した上で**、①② を結線し、③ と △✕ を除外する判断を記録する。

Jev の性質のうち、設計に影響したもの:

- **文章生成・計算・日付比較ができない** → 閾値比較・正規表現・依存グラフには使えない
- **`state` 32k / リクエスト 64k トークン上限** → コードを読んで検証することはできない
- **日本語は英語より精度が落ちる** → ハーネスの入力（issue 本文・findings・観測）は全て日本語
- **出力トークンは無料・入力 $0.042/Mtok** → 判定を並列に大量投入しても安い
- **hosted early-access のみ。weights 非公開・self-host 経路なし**

## 決定

### 決定A: 任意依存の枠に入れる（context7 / code-review-graph / LSP と同格）

`JEV_API_KEY` 未設定でハーネスは従来どおり動作し、**フォールバックは「従来の LLM 判断」**
＝導入前の挙動そのものである。上流が停止・値上げ・仕様変更しても機能が失われないため、
hosted only・weights 非公開を許容できる（context7 のホスト型サーバー経路と同じ受け入れ方）。

**MCP サーバーとしては結線しない。** Jev は HTTP API であり、`scripts/jev-ask.sh`
（curl + 素の bash。jq 不要）から直接叩く。そのため `.claude-plugin/plugin.json` の
`mcpServers` には現れない。

鍵は環境変数（`JEV_API_KEY` / 上流公式の名前 `TYPESAFE_API_KEY`）か
`${HOME}/.claude/dev-workflow/jev.env`（ハーネス非注入原則の置き場所）に置く。
**鍵ファイルは `source` せず自前で1行パースする** — 鍵ファイルに任意のシェルコードを書ける
経路を作らないため。

**エンドポイントは公式ドメインに固定する: `https://api.typesafe.ai/v1/systemone`**
（鍵の発行は `console.typesafe.ai/keys`、仕様は `docs.typesafe.ai`）。
本 ADR の実装中、検索上位に出た `jevmodel.org` を公式と誤認して実装し、実鍵を送信する
事故を起こした。同サイトは自ら「independent and is not affiliated with, endorsed by, or
operated by TypeSafe AI」と明記している非公式の解説サイトでありながら、
`/v1/systemone` で鍵を検証する API と自前の `dashboard/` を自ドメインで運用している。
**`JEV_API_URL` の既定値を公式以外へ向けてはならない**（上書きは可能だが、既定は公式のみ）。

### 決定B: 結線するのは2か所だけ（①②。③ は決定Cで除外）

| # | 判断点 | 型 | 既定 | 安全側への倒し方 |
|---|---|---|---|---|
| ① | 指摘の重複排除（`review.md` R1マージ step 2） | `Noul` | 鍵があれば有効 | `noul < 0.85` なら**統合しない** |
| ② | feedback 台帳の分類（`feedback/SKILL.md` Phase 2） | `Choice`×2 + `Score` | 鍵があれば有効 | `scope` は `choice` のまま（誤り方が安全側へ偏る）/ `category`→`other` / `severity`→`low` |
| ③ | 確度判定のトリアージ | `Noul` | **結線しない** | 決定C を参照 |

呼び出し形・しきい値・記録の作法の正本は `core/references/jev-assist.md`。

**① を本命とした理由**は失敗コストの非対称性にある。統合漏れは二重 issue が立つだけで
成果物は壊れないが、誤統合は severity の低い側の指摘を本文ごと失う。「迷ったら統合しない」
という安全側が明確に定義でき、適合条件3を満たす。現状ここに親エージェントの読解コンテキストが
丸ごと使われているため、削減量も最も大きい。

**② を結線できた理由**は、`skills/feedback/references/scope.md` の判定基準が **すでに
criteria としてそのまま写せる形**になっていること。`key` と `summary` は文字列生成なので
Jev では作れず、従来どおり人間（実行者）が付ける。

**当初は「判断できない → `project` に倒す」という `scope.md` の既定の倒し方を、Jev の
`confidence` へそのまま結線する設計だった。これは測定で否定され撤回した**
（下記「測定結果 ②」）。安全側は確率で倒さずとも、誤り方が安全側へ偏ることで守られている。

### 決定C: ③ は結線しない（測定で効果を否定した）

③ だけは**確度判定（opus）を省略する**方向に効く。`review.md` は「high の指摘であっても、
確度判定を経ずに黙って捨てる経路は無い」と規定しており、検証を省く経路は安全網を1枚薄くする。

**測定の結論は「効果なし」である。** 158件中、素通ししきい値 0.95 に達した指摘は0件で、
削減効果は 0%（下記「測定結果 ③」）。Jev がクラス分離に失敗したからではなく、
**コードを読めない自分の限界を正しく校正して高い確率を返さない**ためである。

当初は `DEV_WORKFLOW_JEV_TRIAGE=1` による opt-in として残す案を採ったが、
`docs/optional-mcp-tools.md`「外す判断基準」の**「効かなければ外す。入れたまま複雑さだけ
残すことをしない」**に従い、**結線とフラグを削除した。** 効果が確認できていない経路を
既定で無効のまま置いておくことは、設定項目と分岐を増やすだけで何も生まない。

**再測定は結線なしに行える**（`jev-shadow-eval.sh run --case 3`）。評価用スクリプト側の
`--case 3` は、確度判定の運用が進んで `low-conf` の事例が蓄積したときに判断を見直せるよう
残してある。

**復活させる場合の制約**（計測で否定されたのは効果であって、この制約ではない）: 向きは
**素通しさせる側だけ**に限る。Jev はコードを読んで検証できないため opus の置き換えにはならず、
前段の選別にしか使えない。Jev が低い値を返したことを根拠に指摘を格下げ・破棄する経路は
作らない。

### 決定D: 確率をそのまま残す

ハーネスの中核は「状態は GitHub issue と git に置く。だから別セッション・別 CLI から
再開できる」。確率的な判断を挟むため、**`choice` / `noul` / `score` / `confidence` の生の値を
そのまま Epic issue・PR 本文・台帳の `evidence` に残す**ことを ①②③ すべてで必須にした
（issue #244「構造的な懸念1」）。丸めた結論だけを残す経路は無い。

台帳は TSV のため**列は増やさず** `evidence` の末尾に載せる（既存レコードとの列の食い違いを
避けるため）。

### 決定E: 除外する判断点を明示的に固定する

| 除外する判断点 | 理由 |
|---|---|
| `plan-waves.sh` の依存グラフ・ウェーブ分解 | 決定的アルゴリズム。「Phase は使わず依存グラフだけが唯一の根拠」という設計を確率的判定器で置き換えるのは退化 |
| `watchdog.sh` 停滞判定 / `count-skips.sh` SKIP 形式判定 | 閾値比較と正規表現。Jev は数値・日付比較が不可。推測させると「`skips=unknown` を 0 件と読み替えない」原則を侵す |
| ゲート合否・merge-base 完全一致検証 | 機械的に真偽が定まるものに確率を持ち込む理由がない |
| `check-readability.sh` の緩和 | 可読性原則は「最優先・例外なし」。確率的判定器に**緩和**権限を与えるのは思想に反する（使うなら逆向き＝追加検出の網だけ） |
| `core/instructions.md` の三分類（停止 / 差し戻し / 記録して進む） | criteria には写しやすいが、未知の事象ほど state 外の文脈が効き、誤判定コストが最大（止めるべきものを進める） |
| `grill-me/SKILL.md` のヒアリング打ち切り判定 | やりとりが全て日本語で、Jev の弱点が直撃する |

この除外は `tests/run-tests.sh` の静的検査で固定した（除外対象のスクリプトが `jev` を
参照していないことを検査する）。意図せず結線が広がるのを防ぐため。

## 測定（shadow mode）

`scripts/jev-shadow-eval.sh` が、**ハーネスを1度も動かさずに**過去の実績から精度を測る。
`build` は鍵不要・課金なし。`run` のみ `JEV_API_KEY` を要する。
**このスクリプトはハーネスから呼ばれない**（課金とネットワークを自律ループの経路に入れない。
`tests/run-tests.sh` で静的に固定した）。

### 教師データの出どころと、確認できた限界

**issue #244 が書いた検証方針「過去 Epic のレビュー結果（観点別4本の findings JSON）を
再生する」は、現状のリポジトリでは実行できない。** R1 のマージ前 findings JSON は
どこにも永続化されていない（Epic issue のコメントにも残っていないことを確認した）。
代わりに R2 が作った **review issue**（97件）と、PR 本文の「レビューで挙がった軽微な指摘」
（61件）を使う。

| # | 正例 | 負例 | 測れること | 測れないこと |
|---|---|---|---|---|
| ① | — | 同一 Epic・同一ファイルを指す review issue のペア **25件**（run が「同一趣旨ではない」と判断した結果として別々に立っている） | **誤統合率（偽陽性）** | **統合漏れ（偽陰性）**。マージ前 findings JSON が無いため |
| ② | — | — | `scope` のみ。台帳が空のため `scope.md` の著者ラベル付き例 **14件**（harness 6 / project 5 / neither 3）を使う | `category` / `severity`（教師ラベルが存在しない）。また例文は criteria の元になった文そのものなので**精度は楽観側に出る** |
| ③ | review issue **97件**（確度判定を通った） | 確度判定が `low-confidence` と明記したもの **1件** / 最初から low severity のもの **60件** | **素通し率（＝削減効果）は確実に測れた**（0件なので負例の少なさに依存しない） | 素通しが発生した場合の適合率。厳密な負例が n=1 のため。確度判定（#157・#162）の導入が最近で蓄積が無い |

③ について、**負例の少なさは結論に影響しなかった。** 素通しが1件も起きなかったため、
「素通ししたもののうち何件が誤りか」を測る必要がそもそも生じていない。
削減効果が 0% であることは負例数と無関係に確定する。

### 受入基準（issue #244「決めたいこと」への回答）

**① の誤統合率（偽陽性）が 5% 以下。** 全体一致率ではなく危険な向きだけを基準にする
（失敗コストが非対称であるため）。

### 測定結果（2026-10-05 実測。`jev-1.13.0` / `jev-latest`）

#### ① 指摘の重複排除 — **合格**

| 指標 | 値 |
|---|---|
| ペア数（正解はすべて `different`） | 25 |
| API 失敗 | 0 |
| Jev が「同じ」と判定（＝誤統合） | **0** |
| 誤統合率 | **0.0%**（受入基準 5% 以下） |
| `noul` の平均 / 最大 | 0.144 / **0.50** |

**しきい値 0.85 に対して最大値が 0.50。** 最も紛らわしいペア（#237 と #228。同じ
`skills/run/SKILL.md` を指す別の指摘）でも 0.50 で、しきい値まで 0.35 の余裕がある。
ぎりぎりの合格ではない。

ただし **n=25 では誤統合率 0% でも 95% 片側上限は 11.3% までしか絞れない。**
さらに 25ペア中10ペアが Epic #3 の `sandbox-exec.sh` 一塊に由来するため、独立な実効
サンプル数はさらに小さい。**「5% 以下であることが証明された」のではなく、
「5% を超える兆候が無く、値の分布に十分な余裕がある」が正しい読み方である。**

#### ② feedback 台帳の分類 — **条件付きで合格。当初の倒し方は撤回した**

| 指標 | 値 |
|---|---|
| 件数 | 14（`harness` 6 / `project` 5 / `neither` 3） |
| `scope` 一致率（**採用**: `choice` をそのまま） | **78.6%**（11/14） |
| `scope` 一致率（**撤回**: `confidence < 0.6` なら `project`） | 57.1%（8/14） |
| 誤りの向き | 安全側（`harness`→`project`）3件 / **危険側（`project`→`harness`）0件** |
| `category` / `severity` | 教師ラベルが存在せず測定不能 |

**当初の設計（`scope.md` の「判断できない → `project` に倒す」を confidence に結線する）は
測定で否定され、撤回した。** `harness` が正解のときの Jev の confidence が構造的に低く
（正解3件が 0.33 / 0.31 / 0.31）、誤答した `project` の confidence は高い（0.9 / 0.6 / 0.5）。
この問いでは**低い confidence は「迷っている」の印ではなく `harness` 側の印**であり、
低 confidence を `project` へ倒すと正解だけが潰れる。

`scope.md` の規定は**人間の判断に対する規則**であって、確率値へ機械的に結線してよいもの
ではなかった。**安全側は別の形で守られている** — 観測された誤答は3件すべて安全側の向きで、
他人の issue 欄を汚す向き（`project`→`harness`）は0件だった。

`project`（5/5）と `neither`（3/3）は confidence 0.87〜1.0 で全問正解。弱いのは `harness`
クラスだけである。`category` は目視では11件すべて `scope.md` の表どおりだが、教師ラベルが
無いため**測定値としては扱わない**。

#### ③ 確度判定のトリアージ — **効果を否定。結線を外す候補**

| ラベル | 件数 | 平均 `noul` | 最大 `noul` |
|---|---|---|---|
| `stands`（確度判定を通り issue 化された） | 97 | 0.478 | 0.71 |
| `low-sev`（最初から low severity） | 60 | 0.136 | 0.37 |
| `low-conf`（確度判定が落とした） | 1 | 0.150 | 0.15 |

**158件すべてが 0.80 未満。素通ししきい値 0.95 に達した指摘は1件も無く、削減効果は 0% である。**

重要なのは、これが「Jev が judgement を間違えた」結果ではないこと。**クラスの分離はできて
いる**（`stands` 0.478 対 `low-sev` 0.136）。届かないのは、**Jev が自分の限界を正しく校正して
いる**からである——コードを読まずに「この指摘は確実に成立する」と断言する根拠が無いので、
高い確率を返さない。issue #244 が「Jev はコードを読んで検証できない」と予測したとおりの挙動。

しきい値を 0.70 まで下げれば 97件中2件（2%）が素通しになるが、安全網を薄くする代償に
見合わない。**この結果をもって ③ は結線しないことに決め、フラグも削除した**（決定C）。
評価用スクリプトの `--case 3` だけを再測定用に残した。

#### 日本語入力 + 英語 criteria の実用性（最大の未知への回答）

**①③ では実用水準。②の `harness` クラスでは弱い。**

① は日本語の finding 本文を 25ペアすべて正しく判別し、③ もクラス分離に成功している
（判定自体は機能している）。一方 ② の `harness` 判定は 6件中3件を外した。
`state` に日本語を入れたまま `criteria` を英語で固定する方式は成立するが、
**「この問題は他のプロジェクトでも起きるか」のような、入力文の外側の知識を要する問いでは
精度が落ちる**と読むのが妥当である（①③ は入力文の中だけで閉じる問い）。

#### 費用

実測の課金は入力トークンのみ（出力は無料）。①25件・②14件・③158件の計197リクエストで
入力トークンは1リクエストあたり概ね 300〜700。**$0.042/Mtok なので実測費用は 1 セント未満**。
レイテンシは1件あたり概ね数百 ms で、shadow 計測全体が数分で完了した。

## 影響

### 追加したもの

- `scripts/jev-ask.sh` — Jev クライアント（curl + 素の bash。jq 不要）
- `scripts/jev-shadow-eval.sh` — shadow 評価（ハーネスからは呼ばれない）
- `core/references/jev-assist.md` — ①②③ の呼び出し形・しきい値・記録の作法の正本
- `docs/optional-mcp-tools.md`「Jev（System One Model）」節 — 導入・保証・外す判断基準

### 変更したもの

- `skills/run/references/review.md` — ①（R1マージ step 2）と ③（確度判定）に結線
- `skills/feedback/SKILL.md` — ②（Phase 2）に結線、`evidence` への記録を必須化
- `skills/feedback/references/scope.md` — criteria との二重管理の注記
- `scripts/doctor.sh` — Jev の導入状況を表示

**毎 run の非ブロッキング通知（`check-prerequisites.sh`）には追加しない。** 課金のある
hosted API であり、使う予定の無い利用者に毎回通知するのは雑音になる。利用者が意図して
叩く `doctor.sh` にだけ出す。

### 切り離し方

`DEV_WORKFLOW_JEV_DISABLE=1` で即座に切り戻せる（鍵を消す必要がない）。恒久的に外す場合は
`scripts/jev-ask.sh` と上記3か所の参照を消せばよい。ハーネス本体は `jev-ask.sh` 以外から
Jev を呼ばない。

## 却下した案

### 案1: ④ 三分類（停止 / 差し戻し / 記録して進む）のクロスチェックに使う

issue #244 は「決めさせるのではなく、run の判断と食い違ったときだけ人間に見せる二重判定」を
提案している。二重判定自体は安全だが、**食い違いを人間に見せる経路がハーネスに無い**
（自律実行が前提で、人間の介入点は Epic 承認と PR レビューに限られる）。経路を新設すると
「止めるものを増やす」変更になり、自律性と衝突する。見送る。

### 案2: ③ を既定で有効にし、しきい値を上げて安全性を確保する

しきい値を上げても、**確かめる手段が無い**という問題は解決しない。
`noul >= 0.99` にしたところで、その値が妥当かを検証する負例が n=1 では足りない。
しきい値の調整は測定の代わりにならない。

### 案3: 日本語入力を英訳してから Jev に渡す

日本語精度の弱点を回避できる可能性があるが、**翻訳の誤りと判定の誤りが区別できなくなる**。
また翻訳には文章生成モデルが必要で、Jev に判断を移してコンテキストを節約する目的そのものが
崩れる。criteria を英語で固定し、`state` は日本語のまま渡す方式を採る。
