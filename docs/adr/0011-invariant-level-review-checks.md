# ADR 0011: 修正が同じ性質の欠陥を作り直す事故への対策は、案1・2のみ実装し案3は見送る

## ステータス

承認済み・案3は見送り（issue #197）

## コンテキスト

issue #197 は、Epic #143 / #173 / #174 を通して**「ある欠陥を直した修正が、同じ性質の
欠陥を別の場所に作り直す」**という同型の事故が4回起きたことを報告している。

| # | 修正 | 何を作り直したか | 発見 |
|---|---|---|---|
| 1 | Epic #173 #180 | #118 が解消したはずの `exists` 誤判定の再現 | epic-review |
| 2 | Epic #173 #167 | `git reset --hard` の置き換え先 `git clean` も deny 常連だった | #140 実装中 |
| 3 | Epic #174 #142 | jest 判定を広げた際に `skips=0` を不当に通す経路を新設 | epic-review（#187） |
| 4 | Epic #174 #192 | 同じ差分の #189 が禁止したポーリングループ例を別ファイルに記述 | delta-review（#194） |

共通する原因は、**修正した本人が「元の欠陥の現れ方」だけを直し、「守るべき性質」を
言語化しないまま次へ進む**ことである。テストは新しい振る舞いを固定するだけになり、
「その性質がリポジトリ全体で成り立つこと」は誰も検査していない。

issue #197 は3つの対策案を提示している。

1. `skills/run/references/review.md` の指摘対応手順に「修正が守ろうとしている性質を
   1文で書き、リポジトリ全体で成り立つかを検査するテストを書けないか検討する」指示を追加する
2. `core/references/review-checklist-correctness.md` に「同じ性質の欠陥を別の場所に
   作っていないか」という確認項目を追加する
3. `tests/run-tests.sh` に既にある「不変条件テスト」（`check_no_deny_common_commands`、
   生成物の一致検査、`RUN_SKILL_FLAT` を使った記述検査等）を、個別の回帰テストとは
   区別できる明示的なカテゴリに整理し、「不変条件テストを書くべきケース」をドキュメント化する

issue本文の「スコープの注意」は次のように明記している。

> 上記3案のうち **1 と 2 は記述の追加だけで済む**。3 は既存テストの整理を伴うため、
> **まず 1・2 だけ入れて次の Epic で効果を観測するのが妥当かもしれない**

## 決定

**案1・2を実装し、案3は今回見送る。**

- 案1: `skills/run/references/review.md`（Claude）と `skills-codex/dev-workflow-run/SKILL.md`
  （Codex）の両方で、R2（指摘のissue化）が作成する review issue 本文に
  `## 対応時の指示（#197）` セクションを追加した。review issue は通常のウェーブループ
  （Step 1〜7）に載って処理されるため、対応する generator は run の手順書ではなく
  issue 本文を読む。指示を手順書だけに書いても実装者には届かないため、issue テンプレート
  自体に埋め込むことで実効性を持たせた
- 案2: `core/references/review-checklist-correctness.md` に「修正の妥当性」という
  チェックリスト項目を追加した。これは `core/roles/evaluator.md` の観点表から
  Claude・Codex 双方の evaluator が共通で参照するファイルであり、アダプタ別の追加作業は
  不要である
- 案3（不変条件テストの明示的カテゴリ化）は**今回実装しない**。理由は「見送った理由」節を参照

## 見送った理由（案3）

1. **issue本文が自ら「まず1・2だけ入れて効果を観測するのが妥当」と留保している。**
   案3は「既存テストの整理」を伴い、既存の `check_no_deny_common_commands` 等の呼び出し名・
   コメント規約を変更する必要があるため、影響範囲が案1・2より大きい
2. **案1・2の効果はまだ観測されていない。** issue #197 自身の「判断基準」節が
   「次の1〜2 Epicで、レビュー指摘の対応が同じ性質の欠陥を別の場所に作る事故を起こすか
   どうかを観測する」ことを再開・追加の判断材料としており、案1・2を先に投入してから
   判断するのが issue の意図に沿う
3. **案3は「命名・分類」の効果が測定しにくい。** 「不変条件テスト」というカテゴリ名を
   付けても、実際に新しい不変条件テストが書かれるかどうかは案1（性質の言語化を促す指示）が
   機能するかどうかに依存する。案1が効かなければ、カテゴリを整備しても新規の不変条件テストは
   増えない可能性が高く、先に案1の効果を確認する方が手戻りが少ない
4. **過剰実装を避ける。** issue #197の「スコープの注意」が明記するとおり、
   「あらゆる修正に全体走査テストを要求する」ことは実装コストを跳ね上げる。案3を今回
   実装コストとして払う前に、案1・2という低コストな介入で十分かを見極める方が、
   ponytailラダー（`core/roles/generator.md`）の「これは存在する必要があるか」判断に沿う

## 再開条件

次のいずれかが観測された時点で、案3（不変条件テストの明示的カテゴリ化とドキュメント化）の
実装を再検討する。

1. **次の1〜2 Epicで、案1・2投入後も同型の事故（修正が同じ性質の欠陥を別の場所に作る）が
   再発した場合。** issue #197 自身の「判断基準」に従い、「性質の言語化を促す」だけでは
   不十分と判断し、案3、またはissue #197が示す代替案（指摘対応を別のエージェントにやらせる）
   を検討する
2. **`tests/run-tests.sh` に不変条件テストと個別回帰テストが混在し続けることで、
   新しくテストを書く実装者が「このケースは不変条件テストとして書くべきか」を毎回自力で
   判断せざるを得ず、実際に不変条件として書かれるべきものが個別回帰テストとして書かれてしまう
   事例が観測された場合**

いずれの場合も、再開時は本ADRを更新するか、issue #197を再オープンして案3の実装を追跡する。

## トレードオフ

- **案3を見送ることで、既存の不変条件テスト（`check_no_deny_common_commands` 等）は
  引き続き個別の回帰テストと同じ見た目のまま残る。** 新しくテストを追加する実装者が
  「これは不変条件として書くべきか」を判断する明示的な手がかりは、本ADRと
  issue #197自体を除いて用意されない
- **案1（issue本文への埋め込み）の効果は、対応する generator が実際にその指示を読み、
  性質を言語化し、テストの要否を検討する、という3段階の実行に依存する。**
  どの段階が欠けても効果は出ない。これは「機械的な仕組みで完全には防げない」という
  issue #197自身の限界の指摘とも一致する

## 追記（issue #198）: 案1の実装自身が #197 の失敗パターンを踏んだ

案1で追加した `## 対応時の指示（#197）` という見出しは、**`gh issue create` の heredoc 本文の
中**にあり、そのまま**駆動先プロジェクトの issue 本文**として作成されていた。dev-workflow は
プラグインであり、駆動先リポジトリの `#197` は無関係な issue を指す。GitHub はこれをリンクとして
レンダリングし、実在すれば cross-reference イベントまで残してしまう（issue #198）。

同じ `skills/run/references/review.md` の別の場所には「dev-workflow 自身のリポジトリの値を
駆動先の値として埋め込んではならない（#81 の教訓）」と明記されており、**#197 の修正（案1）
自身が、まさにこの不変条件と、#197 が問題視する「同じ性質の欠陥を修正が別の場所に作り直す」
パターンの両方を踏んでいた。** 見出しから `（#197）` を落とし `## 対応時の指示` とすることで
修正した（Claude 版 `skills/run/references/review.md` と Codex 版
`skills-codex/dev-workflow-run/SKILL.md` の両方）。上記「決定」節の `## 対応時の指示（#197）`
という記述は、案1実装時点の記録として残し、本節で訂正した事実を追記する。

### 不変条件テストを追加したか

issue #198 は「生成される issue / PR 本文の heredoc に dev-workflow 内部の issue 番号を
埋め込まない」ことをリポジトリ全体で検査するテストの追加を検討するよう求めていた。
**このADRが案3として一度見送った「不変条件レベルの検査」を、この#198自身の再発が
体現したことになる。**

検討の結果、**このケースは誤検出なく機械的に検査できると判断し、追加した。**

- `skills/` と `skills-codex/` の全 `*.md` を対象に、`cat <<'BODY'` 〜 `BODY` の
  heredoc本文の範囲だけを抽出する（heredocの外側にある `#197` のような手順書側の
  説明文は対象外。これは`## 対応時の指示`セクションで見た通り、埋め込んでよい場所である）
- 抽出した範囲に対して `#[0-9]+`（`#`の直後が数字）というパターンを検査する。
  プレースホルダ（`#[epic番号]` / `#[番号]` / `#XX` 等）は `#` の直後が `[` や `X` であり
  数字ではないため一致しない。`$ARGUMENTS` 由来の動的な参照も数字を直接書かないため
  一致しない
- 実装前に、修正前の状態（`#197`埋め込みが残っていた状態）でこのチェックを走らせ、
  該当2箇所（Claude版・Codex版）だけが検出され、他の既存heredoc（`skills/epic/SKILL.md`の
  epic/task issueテンプレート、`skills/run/SKILL.md`のスキップコメント・PR本文）には
  誤検出が無いことを確認した
- 修正後（`（#197）`を落とした状態）で同じチェックが0件になること、および一時的に
  別の内部issue番号（例: `#999`）をheredoc本文に書き足すと検出されること（変異テスト）を
  確認した

このテストは `tests/run-tests.sh` に追加し、「issue #198」の回帰として個別ケースではなく
リポジトリ全体を走査する形で固定した。

## 却下した代案

### 案3を先に実装してから案1・2を投入する

案3（既存テストの命名・分類整理）を先に行うと、「不変条件テストとはどのようなものか」の
実例が整理された状態で案1の指示（性質を言語化し、テストを書けないか検討する）を投入できる
という利点はある。しかし、案1・2の効果自体がまだ未検証の段階で案3のテスト整理まで
一度に行うと、効果測定の対象が「案1・2」なのか「案3の整理」なのか切り分けられなくなる。
issue #197の「判断基準」（次の1〜2 Epicでの再発有無の観測）に沿って、まず最小の介入
（案1・2）だけを投入し、変化がなければ案3を含めた追加対策を検討する方が、原因の切り分けが
容易である。
