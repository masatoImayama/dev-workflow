# ADR 0004: レーンのウェーブ横断維持（cross-wave lane reuse）は見送る（未実装のまま）

## ステータス

承認済み（Epic #143 / Task #153、Task #152 で記述を訂正）— **機構は存在するが未検証のため、現状維持（見送り）**

## コンテキスト

Epic #143 後半のタスク群（#153〜#157）は、LLM の推論ターン数と出力トークン量そのものの削減を
狙う。現状 generator は `ウェーブ数 × レーン数` 回 spawn されており、spawn のたびに
(1) `isolation: worktree` による git worktree 作成、(2) 57KB のシステムプロンプト読み込み、
(3) リポジトリの再調査、という cold start コストを払う。レーン**内**のタスク連続処理は Task #52
で既に実装済みだが、**ウェーブをまたぐと必ずレーン（generator）を作り直している。**

`treflebonbon/dotfiles` の ADR-0019 決定5（「Builder-Evaluator ループは issue をまたいで連続処理
してよい。適用範囲は『同一 worktree/branch』であり『単一の連続セッション』ではない」）を参考に、
`SendMessage` 相当の手段で既存のレーンエージェントへ次ウェーブのタスク列を渡し、レーンエージェント
自体をウェーブ横断で使い回せないか検証した。

## 検証したこと（Task #153 時点の記述と、Task #152 による訂正）

Task #153 は「本タスクを実行している generator 自身に割り当てられているツール一覧を確認したが、
サブエージェントを継続させる手段（`SendMessage` 相当）が見当たらなかった」ことを根拠に、
「Claude Code にはその手段が存在しない」と結論した。**この結論は誤りだった。**

Task #152（本Epicの最終整合タスク）でオーケストレータ（run 本体）側から確認したところ、
次の事実が判明した。

- Claude Code には **`SendMessage` ツールが実在する。** `Agent` ツールの説明にも
  「Use SendMessage with the agent's ID or name to continue a previously spawned agent with
  its context intact」と明記されており、**一度起動したサブエージェントを、コンテキストを
  保持したまま継続させることは技術的に可能**である
- generator（サブエージェント自身）にその手段が見えなかったのは事実である。しかし
  **レーンをウェーブ横断で継続させる主体は generator ではなくオーケストレータ（run）である。**
  `SendMessage` はオーケストレータ側のツールであり、generator の道具箱にツールが無いことは
  「run にできない」ことの根拠にはならない。Task #153 はこの主体の取り違えにより、誤った
  結論に至った
- ただし、**本 Epic では実際に cross-wave 継続を実装・実地検証してはいない。** 「機構が
  存在することは確認できたが、run の Step 3〜Step 5 のループへ組み込んで動かした実績は無い」
  というのが Task #152 時点の正確な状態である

## 決定

**レーンのウェーブ横断維持は、本 Epic のスコープでは実装しない（見送り）。** 現行どおり、
ウェーブごとにレーン数ぶんの generator を新規 spawn する方式を維持する。

見送りの理由は「手段が存在しないから」ではなく、**「機構（`SendMessage`）は存在すると
確認できたが、次の理由により本 Epic のスコープでは実地検証まで手が回らなかったから」**である。

- `SendMessage` によるレーン継続は、run の Step 3〜Step 5（レーン起動・タスク割り当て・
  取り込み検証）の制御フローを、ウェーブ境界をまたいで状態を保持する形に作り替える必要があり、
  影響範囲が本 Epic の他タスク（#144〜#151, #154〜#157）と独立にレビューできる粒度を超える
- 実地検証（実際に複数ウェーブにわたってレーンを継続させ、cold start コストが実測でどれだけ
  下がるかを確認する）には、少なくとも1 Epic分の run 実行が要る。Task #152 は Epic 末の
  最終整合タスクであり、新規機構の実地検証を行う想定のタスクではない

- `skills/run/SKILL.md` Step 3 に、上記の訂正後の事実（機構は存在する／本Epicでは未検証）を
  明記し、「バッチ内の動的レーン補充ができない」（既存の制約。こちらは技術的制約として維持）と
  「バッチ間＝ウェーブ間のレーン継続を本Epicでは実装していない」（未検証による見送り）を
  区別して書く
- `WAVE_BASE` へのベース合わせは、引き続き「レーンの先頭（＝各ウェーブで新規 spawn された
  直後）で1回だけ」のままでよい。**タスク境界／ウェーブ境界という書き分けは行わない**
  （レーンがウェーブをまたいで生存する場合にのみ意味を持つ区別であり、生存しない以上、
  区別を導入すること自体が存在しない概念にラベルを貼ることになる）
- `scripts/cleanup-lane-worktrees.sh` によるレーン worktree の後片付け（Epic 末に一括実行）は、
  レーンがウェーブごとに使い捨てられる前提と矛盾しない
- **余ったレーンの扱い**: レーンがウェーブをまたいで維持されない以上、「前ウェーブで使った
  レーンが今ウェーブでは不要になる」という状況自体が発生しない。各ウェーブは毎回、その
  ウェーブの `subbatch` 列に必要な本数だけ新規に generator を spawn する（既存の
  `plan-waves.sh` の配分ロジックのまま）。したがって本 ADR に起因する追加対応は不要である

## 却下した代案

### フォールバック切り替え用の環境変数を用意する案

Task #153 の要件には「フォールバック経路（従来の毎ウェーブ spawn）を環境変数で選べるように
する」とあるが、これは「cross-wave 継続」と「毎ウェーブ spawn」という**2本の実装済みコードパス**
が存在することを前提にした要件である。cross-wave 継続は（機構としては存在するが）本 Epic では
実装していないため、実装済みの代替コードパスがそもそも存在しない。存在しない機能を選択する
ための環境変数を追加することは、切り替え先が無い分岐を持つデッドコードを増やすだけであり、
ponytail の7段ラダー1段目（「これは存在する必要があるか？」）で「いいえ」と判定した。
**Task #153 完了条件の「継続できない場合: 従来どおりの経路のまま、確認結果と理由が記録されている
（無理に実装しない）」を優先し、環境変数は追加しない。**

## トレードオフ

- **cold start コストの削減という Task #153 の当初目的は、本 Epic では達成されない。**
  `ウェーブ数 × レーン数` 回の spawn は変わらず残る
- Epic #143 の他タスク（#154〜#157）が別の角度からトークン削減を狙うことで、この未達分を補う
- **将来、`SendMessage` による cross-wave 継続を実装・実地検証する余地は残っている。** 機構自体は
  存在が確認済みであるため、着手コストは「手段の探索」ではなく「run の制御フローの作り替えと
  実地検証」に限定される。着手する場合は本 ADR を更新（または新しい ADR で上書き）する
