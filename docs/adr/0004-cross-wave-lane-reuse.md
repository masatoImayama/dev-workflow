# ADR 0004: レーンのウェーブ横断維持（cross-wave lane reuse）は実装しない

## ステータス

承認済み（Epic #143 / Task #153）— **検証の結果、不採用（現状維持）**

## コンテキスト

Epic #143 後半のタスク群（#153〜#157）は、LLM の推論ターン数と出力トークン量そのものの削減を
狙う。現状 generator は `ウェーブ数 × レーン数` 回 spawn されており、spawn のたびに
(1) `isolation: worktree` による git worktree 作成、(2) 57KB のシステムプロンプト読み込み、
(3) リポジトリの再調査、という cold start コストを払う。レーン**内**のタスク連続処理は Task #52
で既に実装済みだが、**ウェーブをまたぐと必ずレーン（generator）を作り直している。**

`treflebonbon/dotfiles` の ADR-0019 決定5（「Builder-Evaluator ループは issue をまたいで連続処理
してよい。適用範囲は『同一 worktree/branch』であり『単一の連続セッション』ではない」）を参考に、
`SendMessage` 相当の手段で既存のレーンエージェントへ次ウェーブのタスク列を渡し、レーンエージェント
自体をウェーブ横断で使い回せないか検証した。

## 検証したこと

**「確認できた事実だけを根拠にする」という Task #153 の必須要件に従い、推測での実装は行わず、
実際に確認できる範囲だけを根拠にした。**

- 本タスクを実行している generator 自身が、run（オーケストレータ）から Task tool で起動された
  サブエージェントである。この generator に**現在割り当てられているツール一覧を確認したが、
  「既に完了して結果を返したサブエージェント呼び出しに対して、後から追加のメッセージを送って
  会話を継続させる」ための手段（`SendMessage` に相当するツール）は存在しない**
- Task tool による起動は、1回の呼び出しにつき1回の最終結果が返る往復（request/response）で
  完結する構造であり、run 側から見ても「既に返答済みの特定のサブエージェント・インスタンスを
  指定して会話を継続する」ためのAPIは公開されていない
- 上記はサンドボックス実験ではなく、**本タスクの実行そのものが検証**である（generator は実際に
  Task tool で起動され、そのツール一覧を実地で確認できる立場にある）

## 決定

**レーンのウェーブ横断維持は実装しない。** 現行どおり、ウェーブごとにレーン数ぶんの generator を
新規 spawn する方式を維持する。

- `skills/run/SKILL.md` Step 3 に、検証結果とその根拠を明記し、
  「バッチ内の動的レーン補充ができない」（既存の制約）と
  「バッチ間＝ウェーブ間のレーン継続ができない」（本タスクの検証結果）を区別して書く
- `WAVE_BASE` へのベース合わせ（`git reset --hard`）は、引き続き「レーンの先頭（＝各ウェーブで
  新規 spawn された直後）で1回だけ」のままでよい。**タスク境界／ウェーブ境界という書き分けは
  行わない**（レーンがウェーブをまたいで生存する場合にのみ意味を持つ区別であり、生存しない
  以上、区別を導入すること自体が存在しない概念にラベルを貼ることになる）
- `scripts/cleanup-lane-worktrees.sh` によるレーン worktree の後片付け（Epic 末に一括実行）は、
  レーンがウェーブごとに使い捨てられる前提と矛盾しない。むしろレーンがウェーブをまたいで生存
  しないことが確定したことで、Epic 末の一括クリーンアップという既存設計がそのまま正当化される
- **余ったレーンの扱い**: レーンがウェーブをまたいで維持されない以上、「前ウェーブで使った
  レーンが今ウェーブでは不要になる」という状況自体が発生しない。各ウェーブは毎回、その
  ウェーブの `subbatch` 列に必要な本数だけ新規に generator を spawn する（既存の
  `plan-waves.sh` の配分ロジックのまま）。したがって本 ADR に起因する追加対応は不要である

## 却下した代案

### フォールバック切り替え用の環境変数を用意する案

Task #153 の要件には「フォールバック経路（従来の毎ウェーブ spawn）を環境変数で選べるように
する」とあるが、これは「cross-wave 継続」と「毎ウェーブ spawn」という**2本の実装済みコードパス**
が存在することを前提にした要件である。本 ADR の検証結果は「cross-wave 継続を実現する技術的手段が
確認できなかった」であり、実装済みの代替コードパスがそもそも存在しない。存在しない機能を選択する
ための環境変数を追加することは、切り替え先が無い分岐を持つデッドコードを増やすだけであり、
ponytail の7段ラダー1段目（「これは存在する必要があるか？」）で「いいえ」と判定した。
**Task #153 完了条件の「継続できない場合: 従来どおりの経路のまま、確認結果と理由が記録されている
（無理に実装しない）」を優先し、環境変数は追加しない。**

将来 Claude Code 側にサブエージェント継続の手段が追加された場合は、そのときに改めて検証し、
本 ADR を更新（または新しい ADR で上書き）する。

## トレードオフ

- **cold start コストの削減という Task #153 の当初目的は達成されない。** `ウェーブ数 × レーン数`
  回の spawn は変わらず残る
- Epic #143 の他タスク（#154〜#157）が別の角度からトークン削減を狙うことで、この未達分を補う
- 将来 harness 側の機能追加によって cross-wave 継続が可能になった場合、再検証コストが発生する
  （現時点でその見込みは確認できていない）
