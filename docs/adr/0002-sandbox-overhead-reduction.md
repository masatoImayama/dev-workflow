# ADR 0002: サンドボックス呼び出しオーバーヘッドの削減

- ステータス: 採用
- 関連: Epic #143, Task #145

## 背景

Epic #143 の目的は run の実行時間短縮である。`scripts/sandbox-exec.sh` はコンテナの常駐化
（`docker run --rm` をやめて `docker exec`）とキャッシュの named volume 永続化で既に大きく
最適化されているが、次の2点が残っていた。

1. **呼び出しごとの固定オーバーヘッド**: dockerfile モードでは1回の呼び出しで docker CLI が
   最大7回呼ばれる（イメージ存在確認・コンテナ存在確認・マウント元確認・イメージIDスキュー確認
   ×2・コンテナ再確認・running確認）。実行本体の `docker exec` は最後の1回だけで、残りは
   すべて前置きの検証である。Windows + Docker Desktop での実測では、docker CLI 1回あたり
   約0.21秒、前置きだけで約1.7秒。1 Epic あたりの呼び出し回数はタスク数 × 3〜6回 ＋
   統合ゲートで概ね50〜100回に及び、Epicあたり数分の固定オーバーヘッドになっていた。
2. **並列レーンの共有資源競合**: キャッシュ volume はリポジトリ単位で共有しているため、
   cargo registry・yarn v1 等グローバルロックを取るキャッシュでは並列レーンが直列化することがある。

## 決定1: 検証結果のキャッシュ化（スタンプ）

前置きの検証結果を**スタンプ**として `${DEV_WORKFLOW_STAMP_HOME:-${HOME}/.claude/dev-workflow/stamps}/<コンテナ名>.stamp`
に残し、以降の呼び出しでは前置き検証を省略して `docker exec` へ直行する（fast path）。

### スタンプのキー・置き場・無効化条件

- **キー**: 「コンテナ名（ファイル名に符号化）」「解決イメージID」「正規化済みマウント元」の3点。
  いずれか1つでも現在の状態と異なれば、必ず従来どおりのフル検証に戻る。
- **置き場**: `${HOME}` 配下（`DEV_WORKFLOW_STAMP_HOME` で上書き可能）。リポジトリの追跡ファイルには
  しない（ハーネス非注入原則。`core/instructions.md`「ハーネス非注入原則」の表に当てはめると、
  マーカー・状態ファイルと同じ分類になる）。Epic 専用 worktree と各レーンの isolation worktree は
  同じユーザーの `${HOME}` を共有するため、レーンをまたいでスタンプが再利用できる。
- **無効化条件（fail-safe。迷ったらフル検証）**:
  - `--rebuild` 指定時（スタンプを一切参照せず、常にフル検証）
  - `--reset-cache` / `--down`（コンテナ削除と同時にスタンプも空に truncate して無効化する）
  - スタンプが無い、または読めない場合
  - コンテナ名・解決イメージID・正規化済みマウント元のいずれかが不一致の場合
  - fast path でも「現在のイメージID再確認」と「running確認」の2回は毎回行う。これにより、
    誰かが手動でコンテナを止めた／イメージを差し替えた場合でも、次の1回の呼び出しで検知できる
    （2回に削っても安全側に倒すための最小限の再確認）

### 効果

fast path 成立時、dockerfile モードの docker CLI 呼び出しは「フル検証時の最大7回＋exec」から
「イメージID確認1回＋running確認1回＋exec1回」の計3回に減る。

### compose モードについて

**対象外とする。** compose モードは `compose ps -q` → `container inspect` → `compose exec`
という別系統の前置きを持ち、`docker compose up -d` によるサービス起動・待機を伴うため、
dockerfile モードと同じスタンプ構造をそのまま適用できない（サービスの起動完了待ちを
スキップしてよい条件が dockerfile モードのコンテナ起動確認より複雑になる）。
本 Epic の主眼である「呼び出しごとの固定オーバーヘッド削減」は dockerfile モードでの
効果が大きく（実測3.4秒/呼び出しの主要因）、compose モードは対象を絞って安全側に倒した。
将来 compose モードの呼び出し頻度が支配的になった場合に改めて検討する。

### `--print-plan` への影響

無い。`--print-plan` はスタンプの有無に関わらず docker に一切触れないドライランのままである。

## 決定2: レーンスコープ・キャッシュ

**採用方式: 共有 volume はそのまま維持し、レーン別の書き込み先を「同じ volume 内の名前空間
（サブディレクトリ）」として与える。**

- 呼び出し元 worktree からレーンスコープを導出する。`.claude/worktrees/agent-*` から呼ばれたら
  `agent-xxxx`、それ以外（リポジトリルート・Epic worktree）はすべて `shared`。
- 新しい環境変数 `DEV_WORKFLOW_LANE_SCOPED_CACHE_ENV` に
  `"<環境変数名>=<コンテナ内のキャッシュパス>"` をスペース区切りで宣言できる
  （例: `CARGO_HOME=/root/.cargo/registry`）。
- レーンスコープが `shared` 以外のとき、実行時に `-e <環境変数名>=<キャッシュパス>/lanes/<レーンスコープ>`
  を渡し、実行前にそのディレクトリを作る（`docker exec` モードと compose モードの両方で効かせる）。
- **既定値は空**。宣言が無ければ現行と完全に同一の挙動になる（既存の駆動先を壊さない）。

### なぜ volume を分割しないか

- コンテナは Epic 単位で1個であり、マウントはコンテナ作成時に固定される。レーンごとに別 volume を
  載せるにはレーンごとにコンテナを作る必要があり、「コンテナ = epic」という分離単位を壊す。
- レーンごとに空の volume を割り当てると、**ロック待ちをコールドキャッシュに置き換えるだけ**で、
  多くのプロジェクトでは却って遅くなる。go build cache / go module cache / npm cache / pip cache は
  並行アクセス安全であり、共有した方が速い。ロックで直列化するのは cargo registry・yarn v1 等
  一部のキャッシュに限られる。
- volume 名を変えないので `--reset-cache` / `--ls` / `--down` の契約とガードをそのまま維持できる。
  レーン別サブディレクトリは同じ volume 内にあるため `--reset-cache` で一緒に削除される
  （`--reset-cache` の説明にこの旨を追記した）。

### 既定を空（共有のまま）にする理由と opt-in すべき条件

- 大半のプロジェクトのキャッシュ（go build cache 等）は並行アクセスで問題が起きないため、
  既定で分離すると「ロック待ちの解消」という効果を得られないまま `lanes/<scope>` 配下に
  分散したキャッシュがコールドスタートを繰り返し、むしろ遅くなる。
- opt-in すべき条件: 実測でレーンの待ち時間の大半が特定のキャッシュディレクトリへの書き込み
  ロック待ちであると判明した場合（例: `cargo build` が並列実行で顕著に遅い、yarn v1 の
  `.yarn-integrity` ロック競合が観測される）。判断手順は「該当キャッシュのロック機構を確認する
  → 実測でロック待ち時間を計測する → 待ち時間がコールドキャッシュのコスト（初回ダウンロード
  時間）を上回る場合にのみ宣言する」。

### 却下した代案

- **レーンごとの volume + コンテナ**: 「コンテナ = epic」という分離単位を壊し、コンテナ数が
  レーン数に比例して増える。本 Epic が削減対象とする固定オーバーヘッド（呼び出しごとの
  docker CLI 呼び出し）をレーンの数だけ増幅してしまう。
- **コンテナ内 overlayfs（レーンごとに書き込み層を分離）**: 特権コンテナが必要になり、
  サンドボックスの権限を広げてしまう。
- **共有キャッシュのリードオンリー化**: Go / npm ともに「読み取り専用の下層キャッシュ +
  書き込み可能な上層キャッシュ」という構成を公式にはサポートしておらず、実装コストに見合わない。

## 完了条件との対応

テスト・検証の詳細は Task #145 の完了条件を参照。`tests/run-tests.sh` に
docker CLI 呼び出し回数の削減・キー不一致時のフル検証復帰・`--rebuild` 時のフル検証復帰・
`--print-plan` の `lane_scope` / `lane_cache_env` 出力・`cache_volume_name()` の出力不変を
検証するケースを追加した。
