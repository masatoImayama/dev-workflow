# ADR 0007: symlink 失敗時のコピー・フォールバック（Windows バインドマウント環境の据え置きと、環境非依存の防御策）

## ステータス

承認済み（Epic #173 / Task #139）

## コンテキスト

Windows + Docker Desktop の環境（kikumemo-front、Next.js/yarn、compose モード）で
`/dev-workflow:run` を実行したところ、`scripts/share-prepared-dirs.sh` の symlink 共有が
一貫して失敗し、レーン並列実行が成立しなかった（issue #139）。

```
$ bash share-prepared-dirs.sh --epic epic434 \
    --source ".../.claude/worktrees/epic434" --spec frontend/node_modules
skip	frontend/node_modules	reason	link-failed
prep=run
```

手動の `ln -s` も `Operation not permitted` で失敗すると報告されている。副作用として、
レーン worktree に `.bin` と `node_modules` という空サブディレクトリだけを含む実体ディレクトリが
作られて残り、generator は安全ルール（`rm`/`rmdir`/`unlink` 禁止）により自力で除去できず停止した。

Epic #173 は「ハーネス・OS で実際にできる方法を確認してから設計すること（推測で実装しない）」を
必須要件としている。symlink・ハードリンク・ジャンクション・named volume・コピーのどれが
Windows バインドマウント上で実際に動くかを確かめ、確認できた方法だけを採ることが求められる。

## 確認できたこと・確認できなかったこと（推測で実装しないため）

**本タスクでは issue #139 の元の再現環境（Windows + Docker Desktop・compose モード・実際の
Node.js/yarn プロジェクト）そのものを用意できなかった。** そのため「`ln -s` が実際に
`Operation not permitted` で失敗する」という現象そのものは、本タスクでは再現できていない。

一方で、**dev-workflow 自身のサンドボックス**（`Dockerfile.dev`、dockerfile モード、Alpine +
BusyBox）は、`docker run -v <Windowsパス>:/workspace` によって Windows のバインドマウント上に
コンテナをマウントしており、issue #139 と同じ「Windows バインドマウント上でコンテナ内から
ファイル操作を行う」という条件は満たしている。この環境で、実際にコマンドを実行して次を確認した。

- **`ln -s`**: バインドマウント配下（`/workspace/...`）で、別のバインドマウント配下のパスを
  ターゲットとする symlink の作成に成功した（`[ -d ]` で実体ディレクトリとして辿れることも確認）
- **`cp -al`（ハードリンク木コピー）**: バインドマウント配下から別のバインドマウント配下への
  ハードリンク木コピーに成功した。コピー元とコピー先で `stat -c %i`（inode番号）が一致することを
  確認し、実際にハードリンクであることを検証した
- **`cp -a` / `cp -r`（実体コピー）**: 同様に成功し、`stat -c %i` がコピー元と異なることを
  確認した（独立したファイルであることの検証）
- **`mv -T`（BusyBox の no-target-directory 相当）・`ls -A`**: いずれも利用可能であることを確認した

**確認できなかったこと:**

- issue #139 の実環境（compose モード・実プロジェクト）で `ln -s` が実際に失敗するかどうか
- 上記いずれかのフォールバック手段が、issue #139 の実環境で symlink の代わりに機能するかどうか
- Windows ネイティブのジャンクション（`mklink /J`）: そもそも実行はすべて Linux コンテナ内で
  行う設計（Epic #173「スコープ外」でネイティブ実行モードの追加を明示的に除外している）ため、
  評価対象にならない
- named volume を使う代替案: node_modules をレーンへ届けるには結局ホスト側の Epic 専用
  worktree のパスと紐付ける必要があり、named volume はホストパスと直接対応しないため、
  素朴な volume 化では成立しない。`docker cp` を挟む案は評価コストに対して本タスクのスコープを
  超えると判断し、検討を打ち切った（将来必要になれば別ADRで扱う）

## 決定

### A. symlink 方式は変更しない（第一選択のまま）

上記の理由により、`ln -s` が実際に失敗する環境を再現・確認できていないため、symlink 方式を
別の方式に置き換えることはしない。Windows 以外の環境（Linux/macOS。`ln -s` が通常成功する）を
含め、**symlink が成功する既存動作は一切変更しない。**

### B. 「実体コピー」による段階的フォールバックを追加する

symlink 作成が `link-failed` になったエントリに限り、実体コピー（`cp -a`。失敗時は `cp -r`）を
1回だけ追加で試みる。この経路は symlink が成功する環境では発生しない（`link-failed` が
そもそも出ないため、コードは追加されるが実行はされない）ため、既存動作を壊さない。

コピー先への書き込みは、次のいずれかの状態でのみ行う。

- 対象 `<dir>` が存在しない -> 一時名にコピーしてから `mv` で確定させる（コピーが失敗しても
  実名 `<dir>` には何も現れない。「レーン worktree に空の実体ディレクトリが残らないこと」に対応）
- 対象 `<dir>` が「空の」実体ディレクトリ -> その場に内容を展開する。issue #139 が報告する
  「`ln -s` 失敗の副作用として空ディレクトリが残る」ケースへの対応。**このケース自体は
  本タスクでは再現できていないが、対応しても既存動作を壊さない**（空でなければ何もしない・
  触れない）ため、防御的に組み込む
- symlink・非空の実体・その他何かが既にある -> 触れない（`copyfailed` のまま。安全ルールに
  従い削除は一切行わない）

出力に新しい行種別 `copied\t<dir>` を追加する。`linked` / `copied` / `exists` はいずれも
`prep=skip` に寄与する（従来 `linked` / `exists` だけだったところに `copied` を追加した）。

### C. ハードリンク（`cp -al`）は採用しない

`cp -al` 自体は動作を確認できたが、**意図的に不採用とした。** ハードリンクは共有元と同一
inode を指すため、後続の `--run-prep`（`yarn install` 等）がコピー先へ書き込むと共有元
（Epic 専用 worktree）を書き換えてしまう。これは Review #116 で symlink 方式に対して
対策済みの問題（インストールコマンドが共有元を破壊する）と同種だが、ハードリンクにはその
対策（`--run-prep` 実行前の `unlink`）が効かない（`unlink` はシンボリックリンクの解除であり、
ハードリンクされた実体ディレクトリには使えない）。ディスクI/Oは増えるが、共有元を汚す経路を
新たに作らないことを優先し、実体を完全に独立させる `cp -a`（`-l` を付けない）のみを使う。

### D. `prep=run` かつ `--run-prep` 未指定を明示する警告を追加する

symlink・コピーのいずれのフォールバックも尽きて `prep=run` のまま `--run-prep` も渡されて
いない場合、stderr に明示の `WARNING` を出す。従来はこの状態で exit 0 になり、呼び出し側が
`prep=` 行を見落とすと「何も起きない」ことに気付けなかった（issue #139 の実害）。**終了コードは
変えない**（呼び出し側との互換性を保ち、判断は引き続き `prep=` 行で行う）。

## 理由

- 「確認できた事実だけを根拠に実装する」という Epic #173 の必須要件に従い、確認できなかった
  `ln -s` の実失敗そのものを前提にした設計変更（symlink方式の置き換え）はしない
- 一方で「`link-failed` になった後どうするか」「`prep=run` を呼び出し側が見落とすとどうなるか」は
  環境非依存に改善できる領域であり、実際に確認できた `cp -a` の成功を根拠に、安全側
  （既存動作を壊さない・データを破壊しない）に倒した防御を追加する
- ハードリンクではなく実体コピーを選んだのは、既存のコード資産（Review #116 の
  「symlink 越しに共有元を破壊しない」という設計原則）と一貫性を保つため

## トレードオフ

- **issue #139 の実環境（Windows + Docker Desktop・compose モード）でこのフォールバックが
  実際に機能するかどうかは未検証である。** `ln -s` が失敗する具体的な状況を再現できていない
  以上、「このフォールバックで #139 が解決する」とは断言できない。次に同じ環境で run を
  実行した際に、`copied` 行が出るか・レーンに node_modules が展開されるかを実地で確認し、
  効果が無ければ本ADRを更新するか別の方式（named volume 等）を再検討する必要がある
- **実体コピーはハードリンクより低速でディスクを多く使う。** install 時間の短縮効果
  （ネットワーク・ネイティブビルドを避けられる点は変わらない）は、次回の Windows 駆動先での
  run 実測で検証する（Epic #173 の完了条件どおり、本タスクの完了条件には含めない）
- **コピー・フォールバックが「空の実体ディレクトリを安全に再利用する」経路を持つことで、
  意図せず不完全な既存ディレクトリへ書き込む可能性はゼロではない。** 判定は「中身が完全に
  空であること」を `ls -A` で確認したうえでのみ行い、非空なら一切触れないことで、
  データ損失のリスクを構造的に排除している

## 却下した代案

### ハードリンク（`cp -al`）をコピー・フォールバックの主手段にする

技術的には動作を確認済みだったが、上記「決定 C」の理由（共有元への書き込み経路を新設して
しまう）により却下した。

### `rmdir` で空の実体ディレクトリを事前に除去してから symlink を再試行する

「レーン worktree に空の実体ディレクトリが残らないこと」への対応として、空ディレクトリを
`rmdir`（空ディレクトリにしか成功しないため理論上はデータ損失が起こり得ない）で除去する案も
検討した。しかし `scripts/share-prepared-dirs.sh` 自身の冒頭コメント（安全ルール）が
明示的に「削除コマンド（`rm` / `rmdir`）を使わない」と定めており、この既存の取り決めを
本タスクの範囲で書き換える根拠（`rmdir` が安全である追加の理由づけ）を用意するより、
「空ディレクトリを削除せずその場で埋める」（決定Bの設計）の方が、既存の安全ルールを一切
変えずに同じ結果（空の実体ディレクトリが残らない）を達成できるため、この案を採用した。

### `--allow-copy-fallback` のようなオプトインフラグを追加する

コピー・フォールバックを既定で有効にせず、明示的なフラグでのみ有効化する案も検討した。
しかしこの経路は `link-failed` になったエントリに限定して発生し、symlink が成功する環境
（Linux/macOS 等）では `link-failed` 自体が発生しないためコードパスに到達しない。
オプトインにする必要性が無く、フラグを追加するとむしろ「Windows 環境の利用者が
フラグの存在を知らないと恩恵を受けられない」という新たな運用コストを生むため、既定で
有効にした（ponytail の7段ラダー1段目「これは存在する必要があるか」で、フラグ自体を
不要と判定した）。
