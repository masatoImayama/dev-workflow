# ADR 0007: symlink 失敗時のコピー・フォールバック（Windows バインドマウント環境の据え置きと、環境非依存の防御策）

## ステータス

承認済み（Epic #173 / Task #139）

## コンテキスト

Windows + Docker Desktop の環境（kikumemo-front、Next.js/yarn、compose モード）で
`/dev-workflow:run` を実行したところ、`scripts/share-prepared-dirs.sh` の symlink 共有が
一貫して失敗し、レーン並列実行が成立しなかった（issue #139）。

```
$ bash share-prepared-dirs.sh --epic epic434 \
    --source ".../.claude/worktrees/epic434" --spec frontend/node_modules
skip	frontend/node_modules	reason	link-failed
prep=run
```

手動の `ln -s` も `Operation not permitted` で失敗すると報告されている。副作用として、
レーン worktree に `.bin` と `node_modules` という空サブディレクトリだけを含む実体ディレクトリが
作られて残り、generator は安全ルール（`rm`/`rmdir`/`unlink` 禁止）により自力で除去できず停止した。

Epic #173 は「ハーネス・OS で実際にできる方法を確認してから設計すること（推測で実装しない）」を
必須要件としている。symlink・ハードリンク・ジャンクション・named volume・コピーのどれが
Windows バインドマウント上で実際に動くかを確かめ、確認できた方法だけを採ることが求められる。

## 確認できたこと・確認できなかったこと（推測で実装しないため）

**本タスクでは issue #139 の元の再現環境（Windows + Docker Desktop・compose モード・実際の
Node.js/yarn プロジェクト）そのものを用意できなかった。** そのため「`ln -s` が実際に
`Operation not permitted` で失敗する」という現象そのものは、本タスクでは再現できていない。

一方で、**dev-workflow 自身のサンドボックス**（`Dockerfile.dev`、dockerfile モード、Alpine +
BusyBox）は、`docker run -v <Windowsパス>:/workspace` によって Windows のバインドマウント上に
コンテナをマウントしており、issue #139 と同じ「Windows バインドマウント上でコンテナ内から
ファイル操作を行う」という条件は満たしている。この環境で、実際にコマンドを実行して次を確認した。

- **`ln -s`**: バインドマウント配下（`/workspace/...`）で、別のバインドマウント配下のパスを
  ターゲットとする symlink の作成に成功した（`[ -d ]` で実体ディレクトリとして辿れることも確認）
- **`cp -al`（ハードリンク木コピー）**: バインドマウント配下から別のバインドマウント配下への
  ハードリンク木コピーに成功した。コピー元とコピー先で `stat -c %i`（inode番号）が一致することを
  確認し、実際にハードリンクであることを検証した
- **`cp -a` / `cp -r`（実体コピー）**: 同様に成功し、`stat -c %i` がコピー元と異なることを
  確認した（独立したファイルであることの検証）
- **`mv -T`（BusyBox の no-target-directory 相当）・`ls -A`**: いずれも利用可能であることを確認した
- **`mv -T` の対象が「既存の空の実体ディレクトリ」の場合の挙動（レビュー #177/#178/#179/#180
  対応時に追加確認）**: rename(2) と同じセマンティクスで、既存の空ディレクトリへ上書き的に
  置き換えることに成功した（`<dir>` が存在しない場合の新規作成と、既存の空ディレクトリへの
  置き換えの両方を、同じ `mv -T` 呼び出し1回で扱えることを確認した）
- **`cp -a` / `cp -r` はシンボリックリンクを symlink(2) で再作成する（レビュー #178 で確認）**:
  ソースに `.bin/foo -> ../pkg/foo` のような相対シンボリックリンクを含めて `cp -a` を実行すると、
  コピー先にも同じターゲットを指す**シンボリックリンク**が作られる（実ファイルとしては
  展開されない）ことを確認した。symlink 作成そのものが拒否される環境では、この symlink(2)
  呼び出し自体が失敗するため、`cp -a` / `cp -r` も `.bin` のようなシンボリックリンクを含む
  ソースに対して部分的に失敗することになる。これは机上の懸念ではなく、本フォールバックが
  対象とする状況（`ln -s` が拒否される環境）そのものに直結する事実である
- **`cp -aL` / `cp -rL`（シンボリックリンクを辿って実体をコピーする）の挙動（レビュー #178 で
  確認）**: BusyBox でも `-L` は利用可能で、(a) 相対シンボリックリンク（`.bin/foo ->
  ../pkg/foo`）を実ファイルとしてコピーする、(b) ソースツリー外を指す相対シンボリックリンク
  （yarn workspace 等の `node_modules/pkg -> ../../packages/pkg`）も正しく解決して実体を
  コピーする、(c) リンク先が存在しないシンボリックリンク（dangling symlink）に対しては `cp`
  がそのエントリでエラーを返し、他のエントリは成功したまま全体の終了コードが非0になる
  （部分失敗になるが、壊れた成功にはならない）、ことをそれぞれ確認した
- **BusyBox の `cp` は、コピー先に名前が衝突する既存エントリ（ディレクトリを期待する位置に
  ファイルがある等）があると、そのエントリだけエラーにしつつ他のエントリはコピーを継続し、
  最終的に非0で終了する（部分失敗。レビュー #177 で確認）**: この部分失敗は最終的な終了コード
  で正しく検出できることを確認した（詳細は下記「決定」のB節を参照）

- **`-L` と循環シンボリックリンクの挙動（レビュー #182 で追加確認）**: BusyBox の `cp -aL` /
  `cp -rL` は循環シンボリックリンク（祖先ディレクトリを指す symlink。`self -> ../..` や
  `loop -> .` 等）を検出せず、実測でディレクトリ125段・パス長約4000字・実体5バイトの
  ソースに対し652KBを書き出すまで再帰することを確認した。pnpm の `.pnpm` ストアのような
  相互 symlink 構成のプロジェクトでは珍しい状況ではない。この残骸は決定Bの一時ディレクトリ
  置き場（`.git/worktrees/<lane>/` 配下）に置かれるため、深くなりすぎると
  `git worktree remove --force` を失敗させうる（下記「決定」F参照）
- **コピー元のパス解決（レビュー #181 で発見・修正）**: コピー・フォールバックの初版
  （Task #139・#177/#178/#179/#180）は、コピー元パスを `--source` に渡されたホスト絶対
  パスのままコンテナ内ミニスクリプトへ渡していた。コンテナはリポジトリルートを
  `/workspace` にマウントするため、このホスト絶対パスはコンテナ内には存在せず、`cp` は
  必ず失敗していた（symlink 側は当初から `REL_SOURCE` で相対化していたが、コピー側だけ
  変換が漏れていた）。**この結果、初版のコピー・フォールバックは本番では一度も成立して
  いなかった。** 新規追加された当時のテストは、テスト用スタブがミニスクリプトをホスト上で
  実行するためホストの絶対パスが解決してしまい、この不整合を構造的に検出できなかった。
  修正は `REL_SOURCE`（symlink ターゲットの計算に使うレーン基準の相対パス）をコピー元にも
  流用することで行った（下記「決定」B参照）

**確認できなかったこと:**

- issue #139 の実環境（compose モード・実プロジェクト）で `ln -s` が実際に失敗するかどうか
- 上記いずれかのフォールバック手段が、issue #139 の実環境で symlink の代わりに機能するかどうか
- `-L` によるディレクトリ・シンボリックリンクの重複コピーが、実際の yarn workspace 構成の
  `node_modules` でどの程度のディスク使用量増加・所要時間増加になるか（#176 で実測予定）
- Windows ネイティブのジャンクション（`mklink /J`）: そもそも実行はすべて Linux コンテナ内で
  行う設計（Epic #173「スコープ外」でネイティブ実行モードの追加を明示的に除外している）ため、
  評価対象にならない
- named volume を使う代替案: node_modules をレーンへ届けるには結局ホスト側の Epic 専用
  worktree のパスと紐付ける必要があり、named volume はホストパスと直接対応しないため、
  素朴な volume 化では成立しない。`docker cp` を挟む案は評価コストに対して本タスクのスコープを
  超えると判断し、検討を打ち切った（将来必要になれば別ADRで扱う）

## 決定

### A. symlink 方式は変更しない（第一選択のまま）

上記の理由により、`ln -s` が実際に失敗する環境を再現・確認できていないため、symlink 方式を
別の方式に置き換えることはしない。Windows 以外の環境（Linux/macOS。`ln -s` が通常成功する）を
含め、**symlink が成功する既存動作は一切変更しない。**

### B. 「実体コピー」による段階的フォールバックを追加する（レビュー #177/#178/#179/#180/#181/#182 で再設計）

symlink 作成が `link-failed` になったエントリに限り、実体コピー（まず `-L` 無しの `cp -a`。
失敗時は `cp -r`。それも失敗した場合に限り `-L` 付きの `cp -aL`。失敗時は `cp -rL`。
`-L` の扱いと順序については決定E・F参照）を1回だけ追加で試みる。この経路は symlink が
成功する環境では**通常**発生しない（`link-failed` がそもそも出ないため）が、レーン側 `<dir>`
が既に「空の」実体ディレクトリとして存在する場合に限っては、symlink 作成が成功する環境でも
この経路が実行される（判定順序4。#180。詳細と旧記述の訂正は決定G参照）。

**初版（Task #139）の実装は、後日の一括レビュー（#177/#178/#179/#180）で4件の不具合を
指摘され、再設計した。** 4件はいずれも「部分的に失敗したコピーを成功として確定させない・
不完全な状態を次回 exists と誤判定させない・レーンの作業ツリーに除去できない残骸を
残さない」という同じ根に対するものであり、個別の継ぎ足しではなく手順自体を作り直した。
**その再設計版も、続く一括レビュー（#181/#182/#183）でさらに3件の不具合を指摘され、
再度改訂した。** 具体的には (1) コピー元パスがホスト絶対パスのままコンテナへ渡っており
コピー・フォールバックが本番で一度も成立しない不具合（#181）、(2) `cp -L` が循環
シンボリックリンクを検出せず削除不能な深い残骸を作る不具合（#182）、(3) 冒頭コメントと
本ADRの記述が実際の挙動と食い違っていた不具合（#183）である。

**コピー元パスの解決（レビュー #181）**: コピー元パスは、symlink ターゲットの計算に使う
`REL_SOURCE`（レーンの作業ディレクトリを起点とした共有元への相対パス）をそのまま流用する。
`--source` に渡されたホスト絶対パスをコンテナ内ミニスクリプトへそのまま渡すと、コンテナは
リポジトリルートを `/workspace` にマウントするためコンテナ内には存在せず `cp` は必ず
失敗していた。symlink ターゲットの計算とは異なり、コピー元はリンクの位置ではなくレーンの
作業ディレクトリ基準で解決されるため、symlink ターゲット計算で行っているリンク位置補正用の
`../` 前置は不要で、`REL_SOURCE` に `<dir>` を連結するだけでよい。`REL_SOURCE` が計算
できない場合（共有元がレーンと同一ファイルシステム上に無い等）は、コピー・フォールバック
自体を試みず従来どおり `link-failed` のままにする。

コピー先の書き込みは、次の**単一の**手順で行う（「対象 `<dir>` が存在しない」場合と
「空の実体ディレクトリとして残っている」場合を分けたコードパスにしない）。

1. 対象 `<dir>` が既に「非空」の実体ディレクトリ、または symlink・その他の非ディレクトリで
   ある場合は一切触れない（`copyfailed` のまま。安全ルールに従い削除は一切行わない）
2. それ以外（`<dir>` が存在しない、または issue #139 が報告する「`ln -s` 失敗の副作用として
   空ディレクトリが残る」ケースを含め「空の」実体ディレクトリとして残っている場合）は、
   `<dir>` とは別の一時ディレクトリを**新規に** `mkdir` し（既に同名の一時ディレクトリが
   残っていれば `mkdir` は失敗し、そのエントリは `copyfailed` として確定させる。古い残骸を
   再利用しての継ぎ足しコピーは行わない）、まず `-L` 無しの `cp -a "<src>/." "<tmp>/"`
   （失敗時は `cp -r "<src>/." "<tmp>/"`）という**内容形**のコピーを試みる。これが失敗した
   場合に限り、循環シンボリックリンクの事前検査（決定F）を経てから `-L` 付きの
   `cp -aL "<src>/." "<tmp>/"`（失敗時は `cp -rL "<src>/." "<tmp>/"`）を試みる（レビュー #182）
3. **確定前に完全性を検証する（レビュー #177）。** `ls -A` によるソースと一時ディレクトリ
   直下のエントリ数が一致する場合に限り「完全」とみなす。一致しない場合、または `cp` 自体が
   非0で終了した場合は `copyfailed` として確定させ、`<dir>` には一切書き込まない
4. 完全性検証を満たした場合のみ `mv -T "<tmp>" "<dir>"` で確定させる。`mv -T` は rename(2)
   相当であり、`<dir>` が存在しない場合はそのまま作成、`<dir>` が「空の」実体ディレクトリ
   として残っている場合はその場所に上書きで置き換える（決定に先立ちサンドボックスで両方の
   挙動を確認済み）ことをどちらも1回の呼び出しで扱える

初版が「対象 `<dir>` が存在しない」場合の再試行（`cp -a "$s" "$tmp" || cp -r "$s" "$tmp"`。
要素形）で `$tmp` が既存ディレクトリの場合にネストしたコピーを作っていた問題（レビュー
#177）は、この手順が (a) 一時ディレクトリを常に新規 `mkdir` してから使う、(b) コピーは
常に内容形のみを使う、という2点により構造的に発生しなくなった。

一時ディレクトリの置き場所も変更した（レビュー #179）。初版は `<dir>.dwtmp$$` としてレーンの
作業ツリー直下に置いていたが、コピーが失敗して残った場合、generator は安全ルールにより
`rm`/`rmdir` を使えず自力で除去できず、駆動先の `.gitignore` にも通常一致しないため
`git status` を汚しコミットに巻き込まれうる。レーンが git worktree である場合（実運用では
常にそう）は、一時ディレクトリを `git rev-parse --git-dir` が指すディレクトリ（git の追跡
対象外）配下に作るよう変更し、レーンの作業ツリーからは一切見えないようにした。git-dir を
解決できない場合（レーンが git リポジトリでない。実運用では起こらないが検証用途等）に限り、
従来どおりレーンの作業ツリー直下へフォールバックし、その場合は残骸のパスを stderr に
明示する。

「空の実体ディレクトリ」の判定自体にも修正が必要だった（レビュー #180）。symlink 方式の
主判定（判定順序2）は当初「`<dir>` が存在すれば無条件に `exists`」としており、コピー・
フォールバックが埋めきれずに空のまま残った `<dir>` を次回実行時に `exists` と誤判定し、
フォールバックが二度と働かなくなる不具合があった。加えて、`ln -s <target> <既存の空
ディレクトリ>` は `<dir>` 自体を symlink に置き換えず「`<dir>` の中に」symlink を作って
しまう（サンドボックスで確認済み）ため、空の実体ディレクトリに対して symlink 作成を
試みること自体が危険と判明した。これを踏まえ、判定順序2を「symlink、または非空の実体・
非ディレクトリの場合のみ `exists`」に変更し、空の実体ディレクトリは symlink 作成を試みず
直接 `link-failed` として確定し、上記のコピー・フォールバック手順に委ねるようにした。

出力に新しい行種別 `copied\t<dir>` を追加する。`linked` / `copied` / `exists` はいずれも
`prep=skip` に寄与する（従来 `linked` / `exists` だけだったところに `copied` を追加した）。

### C. ハードリンク（`cp -al`）は採用しない

`cp -al` 自体は動作を確認できたが、**意図的に不採用とした。** ハードリンクは共有元と同一
inode を指すため、後続の `--run-prep`（`yarn install` 等）がコピー先へ書き込むと共有元
（Epic 専用 worktree）を書き換えてしまう。これは Review #116 で symlink 方式に対して
対策済みの問題（インストールコマンドが共有元を破壊する）と同種だが、ハードリンクにはその
対策（`--run-prep` 実行前の `unlink`）が効かない（`unlink` はシンボリックリンクの解除であり、
ハードリンクされた実体ディレクトリには使えない）。ディスクI/Oは増えるが、共有元を汚す経路を
新たに作らないことを優先し、実体を完全に独立させる `cp -a`（`-l` を付けない）のみを使う。

### D. `prep=run` かつ `--run-prep` 未指定を明示する警告を追加する

symlink・コピーのいずれのフォールバックも尽きて `prep=run` のまま `--run-prep` も渡されて
いない場合、stderr に明示の `WARNING` を出す。従来はこの状態で exit 0 になり、呼び出し側が
`prep=` 行を見落とすと「何も起きない」ことに気付けなかった（issue #139 の実害）。**終了コードは
変えない**（呼び出し側との互換性を保ち、判断は引き続き `prep=` 行で行う）。

### E. コピーには `-L`（シンボリックリンクを辿って実体をコピーする）を付ける（レビュー #178）

`cp -a` / `cp -r` は（`-L` を付けなければ）シンボリックリンクを symlink(2) で再作成する。
symlink 作成そのものが拒否される環境（本フォールバックが対象とする状況そのもの）では、
`node_modules/.bin/*` のようなシンボリックリンクを含むソースに対して `cp -a` / `cp -r` も
同じ理由で部分的に失敗する。実 Node.js/yarn プロジェクトの `node_modules` はほぼ必ず `.bin`
を含むため、`-L` を付けない実装は本フォールバックの主要な対象に対して事実上機能しない。
そのため `cp -aL` / `cp -rL` を使う。

**トレードオフ**: シンボリックリンクがディレクトリを指している場合（yarn workspace 等の
`node_modules/pkg -> ../../packages/pkg`）、`-L` はそのディレクトリの中身を丸ごと重複
コピーするため、ディスク使用量が増える（`.bin/*` のような「ファイルへのシンボリックリンク」
では増加は無視できる規模だが、ワークスペースパッケージへのリンクは規模次第で無視できない
場合がある）。**それでもこのトレードオフを受け入れる。** 理由は上記のとおり、`-L` を
付けない実装は本フォールバックの主要な対象で機能しないため、ディスク使用量の増加は
「フォールバック自体が成立しないこと」に比べて小さい代償と判断した。実際のディスク使用量・
所要時間への影響は #176 の Windows 実環境での実測項目に追加した（本ADR更新時点では未測定）。
**なお循環シンボリックリンクによる無制限の再帰（レビュー #182）はディスク使用量の増加とは
別種のリスク（削除不能な残骸によるレーンの後始末失敗）であり、この決定Eのトレードオフ
判断には含まれない。決定Fで別途防ぐ。**

### F. `-L` は「無しを先に試して失敗時のみ使う」順序に変更し、循環シンボリックリンクは
事前検査で防ぐ（レビュー #182）

決定Eの初版は `-L` を無条件・第一選択として使っていた。これには2つの副作用があった。

1. symlink 作成が実際には成功する環境（Windows 以外に加え、#180 で新たにコピー経路へ
   回るようになった「空の実体ディレクトリ」のケース）でも `-L` の重複コピーが常に発生し、
   決定Eのディスク使用量トレードオフを不必要に負っていた
2. **BusyBox の `cp -aL` / `cp -rL` は循環シンボリックリンク（祖先ディレクトリを指す
   symlink。`self -> ../..` 等）を検出せず、実測でディレクトリ125段・パス長約4000字・
   実体5バイトのソースに対し652KBを書き出すまで再帰することを確認した（レビュー
   #182）。** pnpm の `.pnpm` ストアのような相互 symlink 構成のプロジェクトでは珍しい
   状況ではない。`cp` 自体は最終的に非0で終了し「部分的に失敗したコピーを成功として
   確定させない」という決定Bの目的は守られるが、**残骸の側が問題になる。** この残骸は
   決定Bの一時ディレクトリ置き場（`.git/worktrees/<lane>/` 配下）に置かれ、安全ルールに
   より削除されない。PATH_MAX 級の深さを持つツリーが残ると `git worktree remove --force`
   自体が失敗し、レーン worktree と管理ディレクトリが丸ごと残り続ける
   （`scripts/cleanup-lane-worktrees.sh` は削除失敗を明示的に許容しているだけで、
   解消はしない）。

これを踏まえ、次の2点に変更した。

- **順序**: コピーはまず `-L` を付けない `cp -a`（失敗時は `cp -r`）を試み、それが失敗
  した場合に限り `-L` 付きの `cp -aL`（失敗時は `cp -rL`）を試みる。これにより `-L` に
  実際に触れる経路は、symlink 作成が拒否される環境（本フォールバックが必要になる状況
  そのもの）に限定される
- **循環の事前検査**: `-L` 無しのコピーが失敗し `-L` へ進む前に、
  `find -L "<src>" -mindepth 20 -maxdepth 20` で深さ20を超える経路の有無を検査する。
  該当すれば循環（または想定外に深いツリー）とみなし、`-L` によるコピー自体を試みず
  `copyfailed` に倒す。深さ固定の `find` は循環があっても `-maxdepth` で traversal が
  打ち切られるため、この検査自体が暴走する心配は無い（サンドボックスで実測: 通常の
  `node_modules` はこの深さに到達しないが、循環がある場合は必ず超えることを確認した）

CAP を20とした根拠は、実 Node.js/yarn プロジェクトの `node_modules` が symlink を辿って
到達する実ディレクトリの深さとして20段を超えることは通常想定されない一方、循環がある
場合は数段〜十数段で確実にCAPへ到達することをサンドボックスで確認したため。20は
安全側（誤検知を避けつつ、残骸の最大深さも十分に浅く保つ）に倒した値であり、将来
実測で調整の余地がある。

### G. 空の実体ディレクトリへのコピー経路は symlink 成功環境でも実行される
（レビュー #183。決定Aと冒頭コメントの記述訂正）

決定Aは「symlink が成功する既存動作は一切変更しない」と述べ、決定Bの初版は「この経路は
symlink が成功する環境では発生しない（既存動作を変えない）」と記述していた。**この記述は
`<dir>` が「空の」実体ディレクトリとして既に存在するケースについては誤りだった。**

判定順序4（#180）により、レーン側 `<dir>` が「空の」実体ディレクトリの場合は `ln -s` を
一切試みず無条件に `link-failed` とする。この分岐は `ln -s` の成否と無関係なので、
Linux/macOS のように `ln -s` が正常に成功する環境でも発火する（レビュー #183 でスタブに
より実証済み: `ln` が正常動作するスタブでも `copied` になり、`<dir>` は symlink 化
されなかった）。

**影響は文書の不整合だけではない。** (1) 空の `<dir>` があると全プラットフォームで
`node_modules` 級のディレクトリの全量コピーが走り、決定Fの `-L` 循環リスクにさらされる
経路が増える、(2) コンテナは root で動作するため、コピーされたツリーは root 所有
としてレーンの作業ツリーに置かれ、非 root のホストユーザーからは後始末できない
（従来の symlink・無操作では実体ツリーは作られなかった）。

**判定順序2の変更自体（#180。空ディレクトリを `exists` から除外する）は妥当であり、
変更を戻す必要はない。** 訂正するのは記述のみであり、冒頭コメントおよび本ADRの当該箇所を
「symlink 作成が通常成功する環境でも、`<dir>` が空の実体ディレクトリの場合はコピー経路が
実行される」という実際の挙動に合わせて書き改めた。

## 理由

- 「確認できた事実だけを根拠に実装する」という Epic #173 の必須要件に従い、確認できなかった
  `ln -s` の実失敗そのものを前提にした設計変更（symlink方式の置き換え）はしない
- 一方で「`link-failed` になった後どうするか」「`prep=run` を呼び出し側が見落とすとどうなるか」は
  環境非依存に改善できる領域であり、実際に確認できた `cp -a` の成功を根拠に、安全側
  （既存動作を壊さない・データを破壊しない）に倒した防御を追加する
- ハードリンクではなく実体コピーを選んだのは、既存のコード資産（Review #116 の
  「symlink 越しに共有元を破壊しない」という設計原則）と一貫性を保つため

## トレードオフ

- **issue #139 の実環境（Windows + Docker Desktop・compose モード）でこのフォールバックが
  実際に機能するかどうかは未検証である。** `ln -s` が失敗する具体的な状況を再現できていない
  以上、「このフォールバックで #139 が解決する」とは断言できない。次に同じ環境で run を
  実行した際に、`copied` 行が出るか・レーンに node_modules が展開されるかを実地で確認し、
  効果が無ければ本ADRを更新するか別の方式（named volume 等）を再検討する必要がある
- **実体コピーはハードリンクより低速でディスクを多く使う。** install 時間の短縮効果
  （ネットワーク・ネイティブビルドを避けられる点は変わらない）は、次回の Windows 駆動先での
  run 実測で検証する（Epic #173 の完了条件どおり、本タスクの完了条件には含めない）
- **コピー・フォールバックが「空の実体ディレクトリを安全に再利用する」経路を持つことで、
  意図せず不完全な既存ディレクトリへ書き込む可能性はゼロではない。** 判定は「中身が完全に
  空であること」を `ls -A` で確認したうえでのみ行い、非空なら一切触れないことで、
  データ損失のリスクを構造的に排除している
- **一時ディレクトリの残骸は、削除できないまま蓄積する。** 決定Bのとおり、コピーが繰り返し
  失敗する状況（レーンが git worktree の場合）では、一時ディレクトリを `git-dir` 配下に
  作ることでレーンの作業ツリー・`git status` からは隠せるが、安全ルール（`rm`/`rmdir` を
  使わない）により**削除自体は行わない**ため、失敗が繰り返されるとこの領域にゴミが
  蓄積することを許容している。git worktree はレーンの終了時に丸ごと破棄される運用のため
  実害は限定的だが、根本的な「ゴミが増え続ける」性質そのものは解消していない。
  **この「蓄積を許容する」という受容判断は、残骸がレーンの後始末（`git worktree remove`）を
  失敗させない範囲でのみ成立する（レビュー #182）。** 残骸が `git-dir` 配下に隠れていても、
  深さが PATH_MAX 級に達すれば `git worktree remove --force` 自体が失敗しうる
  （`scripts/cleanup-lane-worktrees.sh` はそのような削除失敗を明示的に許容しているだけで、
  worktree 自体は残り続ける）。決定Fの循環検査は、この前提が崩れないよう残骸自体の深さを
  構造的に抑えるために導入したものであり、置き場所の工夫（本項）と循環検査（決定F）は
  独立にではなく組み合わせて初めて「蓄積を許容できる」という結論が成り立つ
- **`-L`（決定E・F）による重複コピーのディスク使用量増加は未実測である。** yarn workspace
  構成でどの程度になるかは #176 の Windows 実環境実測で確認する。決定Fの順序変更により、
  `-L` に実際に触れる（=ディスク使用量が増える）のは symlink 作成が拒否される環境に
  限定されるため、影響範囲自体は初版より狭まっている

## 却下した代案

### ハードリンク（`cp -al`）をコピー・フォールバックの主手段にする

技術的には動作を確認済みだったが、上記「決定 C」の理由（共有元への書き込み経路を新設して
しまう）により却下した。

### `rmdir` で空の実体ディレクトリを事前に除去してから symlink を再試行する

「レーン worktree に空の実体ディレクトリが残らないこと」への対応として、空ディレクトリを
`rmdir`（空ディレクトリにしか成功しないため理論上はデータ損失が起こり得ない）で除去する案も
検討した。しかし `scripts/share-prepared-dirs.sh` 自身の冒頭コメント（安全ルール）が
明示的に「削除コマンド（`rm` / `rmdir`）を使わない」と定めており、この既存の取り決めを
本タスクの範囲で書き換える根拠（`rmdir` が安全である追加の理由づけ）を用意するより、
「空ディレクトリを削除せずその場で埋める」（決定Bの設計）の方が、既存の安全ルールを一切
変えずに同じ結果（空の実体ディレクトリが残らない）を達成できるため、この案を採用した。

### `--allow-copy-fallback` のようなオプトインフラグを追加する

コピー・フォールバックを既定で有効にせず、明示的なフラグでのみ有効化する案も検討した。
しかしこの経路は `link-failed` になったエントリに限定して発生し、symlink が成功する環境
（Linux/macOS 等）では `link-failed` 自体が発生しないためコードパスに到達しない。
オプトインにする必要性が無く、フラグを追加するとむしろ「Windows 環境の利用者が
フラグの存在を知らないと恩恵を受けられない」という新たな運用コストを生むため、既定で
有効にした（ponytail の7段ラダー1段目「これは存在する必要があるか」で、フラグ自体を
不要と判定した）。
