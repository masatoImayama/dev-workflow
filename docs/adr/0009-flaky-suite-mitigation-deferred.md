# ADR 0009: 統合ゲートの flaky スイート対策（issue #114）は、前提が未確認のため独立実装を見送る

## ステータス

承認済み・見送り（Epic #173 / Task #114）

## コンテキスト

issue #114 は、`/dev-workflow:run` のレーン並列実行中に発生した実測（kikumemo-front
Epic #418、lanes=3、Windows 11 + Docker Desktop）を報告している。レーンごとの `yarn install`
が並行して走り、コンテナ内 I/O が輻輳している間に、変更と無関係なテストスイート
（`HearingDashboard.inline-edit.test.tsx`）がタイムアウトで2回 flaky 失敗し、いずれも
統合ゲートの不合格として扱われた（実際には回帰ではない）。

issue #114 自身が、対策の要否を次のように条件付けている。

> issue #104（レーン worktree ごとの install がフル実行される件）の副作用として観測された。
> #104 の対策（Epic #105: 準備成果ディレクトリの共有）で **I/O 輻輳の主因である並行 install が
> 無くなる**ため、まず Epic #105 の効果を実測してから、本件を独立した対策が必要な問題として
> 扱うかどうかを判断する。

Epic #173 本文の「実行順序について」も同じ判断を明記している。

> **#114 は「独立した対策が必要かどうかの判断」から始まるタスクである。** #104 の対策で
> I/O 輻輳の主因が消えれば、追加の対策は不要と結論してよい（その場合は結論と根拠を
> issue に残してクローズする）。

つまり本タスクの成果物は、まず「I/O 輻輳の主因（並行 install）が本当に消えたか」を確認し、
その結果に応じて対策の要否を判定することである。

## 確認できたこと・確認できなかったこと（推測で実装しないため）

### 確認できたこと

1. **issue #114 が前提としていた「Epic #105（準備成果ディレクトリの共有）の効果」は、
   Epic #173 の先行タスクとして扱われた。** 本 Epic のタスク一覧のうち、#117 / #118 / #139 が
   `share-prepared-dirs.sh` の共有経路の不具合修正（symlink 失敗パスの是正、
   `cp -a` コピー・フォールバックの追加）にあたる。`docs/adr/0007-share-prepared-dirs-copy-fallback.md`
   に記録済み。

2. **#104（named volume 化）は「据え置き」で完了した。** `docs/adr/0008-node-modules-named-volume-deferred.md`
   に記録のとおり、named volume 化は実装されておらず、`node_modules` をレーンへ届ける役割は
   引き続き #139 のコピー・フォールバックが担っている。

3. **#139 のコピー・フォールバック（`ln -s` 失敗時に `cp -a` を試みる経路）は、
   issue #139 の実環境（Windows + Docker Desktop・compose モード・実際の Node.js/yarn
   プロジェクト）で実際に機能するかどうかが、ADR-0007 の時点で「確認できなかったこと」
   として明記されたまま残っている。**引用（ADR-0007 より）:

   > issue #139 の実環境（Windows + Docker Desktop・compose モード）でこのフォールバックが
   > 実際に機能するかどうかは未検証である。

4. **同じ未検証事項は #176（Windows 実環境での効果測定）として、Epic #173 とは別の issue に
   切り出されている。** #176 の「やること」1番目は「Windows + Docker Desktop の node 系駆動先で
   run を1本実測する」であり、その実測がまだ行われていないことが issue 本文から読み取れる
   （`state: OPEN`、着手を示すコメント無し）。

5. **したがって、issue #114 が対策の要否判定の前提としていた「I/O 輻輳の主因である並行 install
   が無くなる」ことは、実環境ではまだ確認されていない。** コードレベルでコピー・フォールバックの
   経路が追加されたことと、それが実際に Windows + Docker Desktop の compose モードで
   `linked` または `copied` を返し `yarn install` の並行実行を回避することとは、別の事実である。
   後者は #176 の実測を待つ必要がある。

### 確認できなかったこと

- Windows + Docker Desktop 実環境で、#139 のコピー・フォールバックが実際に `yarn install` の
  並行実行を回避するかどうか（#176 の実測待ち）
- 上記が回避されなかった場合に、issue #114 が報告した I/O 輻輳由来の flaky 失敗が
  実際にどの程度残るか（そもそも輻輳が解消されなければ、当然ながら flaky 失敗も解消されない
  可能性が高いが、これも実測なしには断定できない）
- I/O 輻輳が解消された場合に、それでもなお flaky 失敗が残るかどうか（輻輳以外の原因
  ――例えばコンテナ全体のリソース制約――が寄与している可能性は、issue #114 の実測記述からは
  排除できない）

## 決定

**issue #114 に対する独立した対策は、本タスクでは実装しない（見送る）。**

理由は、issue #114 自身および Epic #173 本文が明示する前提条件（「#104/#105 系の対策で
並行 install が無くなったこと」）が、実環境でまだ確認されていないためである。前提が
確認できていない以上、それに基づく対策の要否判定自体ができない。ここで「対策が不要」と
断定することも「対策が必要」と断定することも、いずれも推測に基づく判断になり、
Epic #173 の完了基準4（「確認できた事実だけを根拠に実装されていること。確認できなければ
従来動作のまま据え置き、確認結果と理由が ADR に残っていること」）に反する。

また issue #114 の「検討時の注意」が明示的に禁止する「統合ゲートへの単純なリトライ」は、
そもそも本判断とは独立に不採用である。flaky と回帰を機械的に区別する根拠（同一コミットでの
再実行結果の比較、失敗スイートが当該ウェーブの差分と無関係であることの判定など）を伴わない
限り、「落ちたテストを握り潰す」方向の変更になり、ハーネス共通ルールの「SKIP を通過扱いに
しない」という既存方針と衝突する。仮に前提が確認できていたとしても、単純リトライは採用しない。

**コード変更は行わない。既存の統合ゲート・再試行フロー
（`skills/run/references/recovery.md`「原因ウェーブの特定」―― 原因ウェーブを特定した上で
generator に実際の修正をさせてから再実行する、という既存の仕組み）をそのまま維持する。**
この既存フローは「原因を特定して直してから再実行する」ものであり、issue #114 が禁止する
「単純なリトライ（原因を特定せず握り潰す）」とは異なるため、変更の必要はない。

## 理由

- issue #114 / Epic #173 本文がそろって「まず前提を実測してから判断する」という手順を
  明示しており、その実測（#176）がまだ行われていない
- 前提の実測結果が無いまま対策を実装すると、#176 の実測後に「輻輳は既に解消していた
  （対策は不要だった）」または「輻輳は解消していない（対策の設計が的外れだった）」の
  いずれであっても、無根拠な実装として手戻りになる
- 「何もしない」という判断も、根拠と再開条件を記録しなければ Epic #173 の完了基準3
  （設計判断の docs/ 配下への文書化）を満たさない。そのため対策そのものは実装せず、
  この ADR で判断と再開条件を記録する

## 再開条件（#176 の実測とどう連動するか）

次のいずれかが #176 の実測で判明した時点で、本 ADR を更新するか、issue #114 を再オープンして
独立実装を検討する。

1. **輻輳が解消されなかった場合**（`share-prepared-dirs.sh` の出力が `link-failed` のまま
   `copied` に進まない、または `copied` になっても複数レーンの `yarn install` が依然として
   並行に走る）: issue #114 が報告した flaky 失敗が再現するかどうかを実地で確認し、
   再現すれば「flaky と回帰を機械的に区別する根拠を伴う設計」（同一コミット再実行比較・
   差分無関係判定等）を新たな ADR として起こす
2. **輻輳は解消したが、それでも無関係スイートの flaky 失敗が観測された場合**: 輻輳以外の
   原因（コンテナ全体のリソース制約等）を切り分けたうえで、対策の要否を改めて判断する
3. **輻輳が解消し、flaky 失敗も観測されなかった場合**: issue #114 をクローズし、本 ADR に
   その事実を追記する

いずれの場合も、#176 が実測データを持ち帰るまでは本判断（見送り）を維持する。

## トレードオフ

- **issue #114 が報告した実害（同一 run 中に2回の flaky 失敗、統合ゲートの誤った不合格判定）は、
  本タスクでは未解消のまま残る。** 次に Windows 実環境で run を実行した際、輻輳が実際に
  解消していなければ、同種の flaky 失敗が再発しうる
- **前提が確認できるまで待つ判断は、issue #114 の解決を #176 の完了に依存させる。** #176 が
  長期間着手されない場合、本 issue も長期間 未解決のまま残ることになる

## 却下した代案

### 前提の確認を待たず、機械的な flaky/回帰判定ロジックを先に実装する

「輻輳が解消していてもいなくても、flaky と回帰を区別できる仕組みは有用ではないか」という
案も検討した。しかし issue #114 が報告した実害はあくまで「I/O 輻輳という特定原因による
flaky 失敗」であり、その原因が本当に解消したかどうかが未確認の段階で、原因に応じた
判定ロジック（差分無関係性の判定基準、再実行のタイミング等）を設計すると、#176 の実測後に
設計の前提（どの程度の頻度で・どの条件で flaky が起きるか）が変わり手戻りになる可能性が高い。
Epic #173 の完了基準4（推測で実装しない）に従い、実測データが揃うまで設計自体を保留する。

### 統合ゲートに単純なリトライを追加する

issue #114 の「検討時の注意」で明示的に禁止されている。flaky と回帰を区別する機械的根拠を
伴わない単純リトライは、失敗したテストを無条件に握り潰す挙動になり、ハーネス共通ルールの
「SKIP を通過扱いにしない」という既存方針と衝突するため、前提の確認状況に関わらず不採用。
