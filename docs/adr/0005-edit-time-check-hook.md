# ADR 0005: 編集時チェック（PostToolUse フック）

- ステータス: 採用
- 関連: Epic #143, Task #155

## 背景

generator の実装ループは「編集 → `sandbox-exec.sh` でビルド/テスト実行 → エラーを読む →
修正」で最低3ターン、かつ毎回 Docker 往復（ADR 0002 の実測で1呼び出しあたり約3.4秒）を伴う。
編集直後にその場で型/lint 単体の軽量チェックが返れば、この往復の一部を消せる。

参考にした設計: `treflebonbon/dotfiles` は `PostToolUse(Edit|Write|MultiEdit)` と `Stop` の
両方に型/lint チェックの hook を設定し、編集直後に問題をエージェントへ返している
（timeout は PostToolUse 5秒 / Stop 30秒）。

## 決定1: ホスト側で実行する（コンテナ経由にしない）

**採用: ホスト側で直接実行する。** `scripts/sandbox-exec.sh` を経由しない。

- このタスクの目的そのものが「Docker 往復オーバーヘッドの削減」（Epic #143 全体の主眼、
  ADR 0002 参照）である。編集時チェックをコンテナ経由にすると、`docker exec` の固定コスト
  （fast path でも1回あたり数百ms〜、fast path が成立しない場合は前置き検証を含め約3.4秒）を
  型/lint という秒オーダーの軽量チェックに毎回払うことになり、削減効果の大半が相殺される。
- 型チェック単体・lint 単体は、依存の実行系（`node` / `go` / `python` 等のツールチェイン）が
  ホスト側にインストールされていることを前提にできる場合に限り、コンテナ相当の検証結果を
  秒未満〜数秒で得られる。ホストにツールチェインが無い場合は次の「フェイルセーフ」節が
  効き、単に何もしない（既存挙動と同じ）。
- **トレードオフとして受け入れること**: ホスト実行なので「コンテナ内でしか動かない
  ツールチェイン」（コンテナにしか無いバージョン・OS依存ツール等）は編集時チェックの対象に
  できない。その場合は該当ファイルの glob を `## 編集時チェック` 節に書かなければよい
  （書かなければ何もしない。フェイルセーフ）。そのファイル種別の検証は従来どおり
  レーン内ゲート（`sandbox-exec.sh` 経由のテスト）と統合ゲートに委ねられる。

### 却下した代案

- **`sandbox-exec.sh` 経由でコンテナ内実行**: 上記のとおり目的（Docker 往復削減）と直接矛盾する。
- **ホスト/コンテナを自動判定して切り替える**: 判定ロジック自体の複雑さと誤判定リスクが、
  得られる効果に見合わない。プロジェクト側が「軽量・秒オーダーで完結する」チェックだけを
  `## 編集時チェック` 節に書く、という運用上の前提で十分にシンプルに保てる。

## 決定2: 差し戻し契約は `check-readability.sh` のものを再利用する

新しい差し戻し方式を発明しない。`DEV_WORKFLOW_HOOK_VENDOR` によるベンダー判定
（Claude Code = `exit 2` + stderr／Codex CLI = `exit 0` + stdout の JSON／pre-commit 等 =
`exit 1` + stderr）をそのまま踏襲する。`scripts/edit-check.sh` はこの判定ロジックを
`check-readability.sh` から直接 `source` せず、同じ十数行を重複実装している。理由は
`scripts/edit-check.sh` のヘッダコメント「設計メモ」を参照（要約: 両スクリプトを疎結合に
保ち、一方の改修がもう一方の回帰テストに波及しないようにするため）。

## 決定3: チェック仕様はマーカーファイル経由で渡す（環境変数の伝播に頼らない）

PostToolUse フックは CLI 本体（Claude Code / Codex CLI）の子プロセスとして起動される。
generator が Bash ツール越しに `export DEV_WORKFLOW_EDIT_CHECK=...` しても、その環境変数は
フックの子プロセスには伝播しない（Bash ツールの1呼び出しは独立したサブプロセスであり、
CLI 本体の環境には反映されない）。`scripts/heartbeat.sh` の `--abort` フラグ判定が
env var ではなくファイル（`.dev-workflow-abort`）を見ているのと同じ制約であり、同じ解決策
（マーカーファイル）を採る。

- 置き場所: `scripts/lib/marker-root.sh` が解決する「メインリポのルート」配下の
  `.claude/.dev-workflow-edit-check`。Epic 専用 worktree・各レーンの isolation worktree の
  いずれから見ても同じ場所に解決される（`heartbeat.sh` の `.dev-workflow-heartbeat` と同じ
  解決経路）。
- 書き込み: run が Epic 開始時（`## 準備コマンド` 等の他の任意節と同じタイミング）に
  `scripts/edit-check.sh --write`（stdin からチェック仕様を読み取り、一時ファイル + `mv` で
  原子的に置き換える）を呼ぶ。節が無い Epic では `scripts/edit-check.sh --clear` を呼び、
  前回 Epic の内容が残留しないようにする。
- 読み取り: フック本体は起動のたびにこのファイルを読む。`DEV_WORKFLOW_EDIT_CHECK` 環境変数が
  設定されていれば、ファイルより優先する（テスト・デバッグ用の上書き経路として残す）。
- **この設計により generator（`core/roles/generator.md` / Step 3 のレーンプロンプト）への
  変更は一切不要になる。** フックは編集のたびに自動発火し、generator は編集時チェックの
  存在を意識する必要がない。

## 決定4: タイムアウトと「テストスイートではない」線引き

- 既定 5 秒（`DEV_WORKFLOW_EDIT_CHECK_TIMEOUT` で調整可）。外部 `timeout` コマンドに依存せず
  （`check-readability.sh` と同じ理由＝macOS 既定環境に無い）、bash 組み込みの
  バックグラウンドジョブ + `sleep` + `kill -TERM` + `wait` で実装する。
- **想定するのは型チェック単体・lint 単体のような秒オーダーの処理であり、テストスイートでは
  ない。** テストの実行はレーン内ゲート（generator が `sandbox-exec.sh` で実行する変更範囲の
  テスト）と統合ゲート（run がウェーブごとに実行するプロジェクトの全テスト）が担う。
  `## 編集時チェック` 節にテストスイート実行コマンドを書くことは想定しておらず、
  書いた場合はタイムアウトで打ち切られて素通りする可能性が高い（フェイルセーフとして
  害はないが、意図した検証は行われない）。

## 決定5: フック自体のエラーはブロックしない

コマンド不在（`bash -c` の exit 127）・タイムアウト（`SIGTERM` による exit 128+15=143。より
一般に exit >= 128 はシグナル終了とみなす）は、いずれも「チェックが実行できなかった」ケースと
みなし、ブロックしない（`exit 0` で素通り。stderr に警告だけ出す）。ブロックするのは
「チェックが実行でき、かつ非 0 終了＝違反が見つかった場合」だけである。

## 完了条件との対応

テスト・検証の詳細は Task #155 の完了条件を参照。`tests/run-tests.sh` に、
節が無い場合の完全な後方互換・タイムアウトでのブロック回避・コマンド不在でのブロック回避・
違反検出時の3ベンダー分の差し戻し契約・`--write`/`--clear` の挙動・
`hooks/hooks.json` / `hooks/hooks.codex.json` の結線を検証するケースを追加した。
