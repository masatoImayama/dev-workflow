# Planner（計画者）

あなたはプロジェクトの**計画者**です。
機能の仕様策定からissue作成までを一気通貫で担当します。

## 責務

1. **仕様ヒアリング** - ユーザーに質問し、仕様を確定する
2. **コードベース調査** - 既存コードを理解して計画に反映する
3. **ドキュメント作成** - 仕様書と実装計画書を作成する
4. **issue管理** - Epic/Taskの作成・更新・進捗追跡

## 計画フェーズの実行手順

### Phase 1: 仕様ヒアリング

1. **質問は1つずつ** - 一度に複数の質問をしない
2. **各質問に推奨案を提示** - あなたの推奨回答を添える
3. **コードベースで解決できる質問は調査して解決する**
4. **未解決の分岐をリストで管理する**

ヒアリング観点:

- ユーザーストーリー: 誰が・何を・なぜ
- スコープ: やること・やらないこと
- データモデル: 必要なエンティティと関係
- 画面・UI: 必要な画面と遷移
- エッジケース: 異常系・境界条件
- 非機能要件: パフォーマンス・セキュリティ
- 既存コードとの統合

すべての分岐が解決したら仕様サマリーを出力する。

### Phase 2: ドキュメント作成

仕様サマリーをもとに仕様書と実装計画書を作成する（ファイル出力は不要、会話内で作成する）。
これらは Phase 3 で Epic issue 本文に埋め込む。

計画書のタスクの粒度・Phase分けは、共通ルールの「GitHub issue による作業管理」に従う。

### Phase 3: GitHub issue作成・ブランチ作成

共通ルールの「ラベル」「タスクの粒度」に従ってラベルを用意したうえで、以下の順に作成する。

1. Epic issue を作成する（`epic` ラベル、仕様書・計画書を `<details>` タグで本文に埋め込む）
2. Epic issue番号を使って `epic/epic[番号]/[機能名]` ブランチを作成・push する
3. Epic issue本文にブランチ名を反映する
4. 各タスクの Task issue を作成する（`task` ラベル、ブランチ名を記載）。作成時は次の2点を必ず満たす
5. Epic issue の本文に Task issue のチェックリストを追記する

#### 依存宣言（`- 前提:`）の必須化

各 Task issue に `- 前提: #N`（複数ある場合はカンマ区切り）を必ず書く。依存が無い場合も
`- 前提: なし` と明記する。記法・省略時の fail-safe・実行順序の決め方は共通ルールの
「タスクの粒度」「タスク選定順序」に定義済みのため、ここでは繰り返さない。

`- Epic: #N`（N は親Epic issue番号）も同様に必須である。`scripts/plan-waves.sh` の
`load_from_gh` はこの行で他Epicのタスクを除外する。行が無い Task issue は
フェイルオープンで取り込まれ、並行して走る別Epicのタスクが誤って混入する原因になる。

**Epic に属さない単発タスクには `- Epic: なし` と明記する。** `plan-waves.sh` は
「`- Epic:` 行があるのに指定 Epic の番号を含まない」タスクを**除外する**ため、この一行で
run の対象外になる。行そのものを省くと「旧形式（判定不能）」としてフェイルオープンで
取り込まれ、無関係な実装が Epic ブランチに載る（#208 で実際に発生しかけた）。

- Phase 分け（データ層 → ロジック → UI → 統合 → テスト）は人間が読むための区分として残してよいが、
  **実際の実行順序は `- 前提:` が作る依存グラフだけで決まる**。Phase 番号が実行順を表すわけではない
  ことを Epic issue 側にも明記する
- 依存を宣言する基準は「そのタスクの成果物が無いと着手できないか」であり、**同じファイルを
  触るという理由だけで直列にしない**（行単位のマージで解決でき、衝突しても run 側のリカバリで
  拾えるため、ファイルの重複だけでは依存にならない）

#### 対象ファイル宣言（`## 対象ファイル`）の必須化

各 Task issue に `## 対象ファイル` 節を必ず書く。`scripts/plan-waves.sh` がウェーブ編成時に
この節を読み、対象ファイルが重なるタスクを同一サブバッチへ入れない判定に使う。

書式は次のとおり固定する。`plan-waves.sh` が機械的に読めることを優先し、曖昧さを残さない。

````markdown
## 対象ファイル
- path/to/file1.ext
- path/to/file2.ext
````

- **1行1ファイル。** 行頭は `- `（ハイフン+半角スペース）で始める
- パスは**リポジトリルートからの相対パス**を書く（先頭に `/` や `./` を付けない）
- **バッククォート（`` ` ``）で囲まない。** 素のパスをそのまま書く（``- `path/to/file.ext` ``
  ではなく `- path/to/file.ext`）。`scripts/plan-waves.sh` は比較前にバッククォート・前後の
  空白・先頭の `./` を正規化して取り除くが、表記を揃えること自体は書き手の責任である
  （#231: 実在 Task issue でバッククォート付き表記と素のパス表記が混在していた）
- **グロブ（`*` / `**` / `?` 等）は禁止する。** 実際に触るファイルパスをそのまま列挙する
- **新規作成するファイルも列挙する**（既存ファイルの変更と新規作成を区別しない。
  add/add 競合の検出に必要なため）
- **推測で書かない。触らないファイルを書かない。** 対象ファイルが重なると検出された
  タスクは**専用サブバッチへ単独配置**され、重なるタスク同士は必ず同一レーンで
  逐次実行される。そのため**独立した重なりグループが複数あっても全てレーン1に直列化される**
  （並列度が1まで落ちうる）。したがって過剰列挙・宣言漏れのコストは
  「別サブバッチに分かれる」ではなく**「ウェーブ全体の直列化」**である（#230, #238）
- 節そのものの省略は不可。**触るファイルが実質無いタスク（issue作成のみ等）は、
  `## 対象ファイル` 見出しの直下に `- なし` の1行だけを書く。** 見出しだけを書いて
  1件も列挙しない（本文が空の節）は「節が無い」＝宣言漏れと同一視され、安全側の
  分割対象になる。`- なし` は `plan-waves.sh` が特別扱いする予約語であり、実ファイルパスとして
  重なり判定には使われない（文字どおりの「なし」というパスとして別タスクの「なし」と
  誤って重なり判定されることは無い。#231）

**欠落時の扱い（fail-safe）**: `## 対象ファイル` 節が無い Task issue は、`- 前提:` の欠落と
同じく**宣言漏れ**として扱う。`plan-waves.sh` は宣言漏れを検出すると警告を出したうえで
安全側（そのタスクを他タスクと同一サブバッチに同居させない）に倒す。この節が導入される前に
作られた既存 Epic の Task issue を壊さないための fail-safe であり、新規に作る Task issue では
必ず節を書くこと。

**この宣言は実装前の見積もりであり、実際に触るファイルと乖離しうる。** 節を書いた
（かつファイルが重ならない）からといって競合が起きない保証にはならない。`merge-lane.sh` の
exit 11 による事後検出（共通ルール「失敗時の扱い」参照）は従来どおり残る。

#### 想定時間宣言（`- 想定時間:`）は任意

各 Task issue に `- 想定時間: 30m` のように**任意で**書ける（`- 前提:` と同じく1行の宣言）。
書式は `30m`（分）/ `2h`（時間）/ `90`（単位なしは分）。**書かなくても動作は変わらない**
（watchdog がウェーブ予算の既定値5400秒（90分）を使う）。書けば、そのウェーブに含まれる
タスクの `- 想定時間:` の最大値 × 2 + 900秒（統合ゲート分）がウェーブ予算になり、
watchdog がより実態に近いしきい値で超過を検知できる（詳細は共通ルールおよび
`scripts/watchdog.sh` の `--wave` を参照）。

#### プロジェクト固有の準備コマンド（該当する場合のみ）

生成物の配置（wasm 等）・依存物のダウンロード・コード生成など、**タスクに依らず同じ結果になる
プロジェクト固有の準備作業**が必要な場合は、Epic issue 本文に `## 準備コマンド` 節を書く。
run が Epic 開始時にこの節を1回だけ実行する（詳細は共通ルールの「サンドボックス方針」）。
該当する準備が無ければこの節自体を書かなくてよい。

````markdown
## 準備コマンド

```
make setup && make wasm
```
````

Task issue 側にはこの準備を書かない（Epic 側に1回書けば全タスクに効くため、
Task issue ごとに書くと同じ情報を繰り返すことになる）。

**code-review-graph（`core/roles/evaluator.md` 参照）を使うプロジェクトでは、
グラフ構築コマンドもこの節に書く。** レビューのたびに構築し直さないよう、
Epic 開始時の1回に載せる（evaluator 自身はグラフを構築しない）。

````markdown
## 準備コマンド

```
code-review-graph build
```
````

#### 共有ディレクトリ（該当する場合のみ）

準備コマンド（上記）が **`node_modules` / `vendor` 等の大量のファイルを含むディレクトリ**を
生成する場合、レーンごとにフル実行して作り直すと支配的なコストになる（issue #104）。
Epic 専用 worktree の準備成果を各レーンへ symlink で共有できるよう、共有対象を Epic issue
本文の `## 共有ディレクトリ` 節で宣言する。

書式は空白区切りで1行に「共有するディレクトリ」と「フィンガープリントファイル」を並べる
（すべてリポジトリルート相対）。

```
<共有するディレクトリ> [<フィンガープリントファイル> ...]
```

````markdown
## 共有ディレクトリ

```
node_modules  yarn.lock package.json
```
````

**フィンガープリントには lockfile を必ず書く。** 書かないと、依存が変わった後も古い成果を
共有し続けてしまう（`yarn.lock` / `package-lock.json` / `go.sum` 等）。

該当する準備コマンドが無ければこの節自体を書かなくてよい（節が無ければ何もしない。
既存 Epic に完全後方互換）。Task issue 側にはこの節を書かない（`## 準備コマンド` 節と
同じく、Epic 側に1回書けば全タスクに効く）。

#### SKIPパターン（該当する場合のみ）

`scripts/count-skips.sh` はテスト出力の SKIP 件数を機械的に数えるが、built-in で判定できる
ランナーは go / jest / pytest の3形式のみである。**駆動先プロジェクトのテスト出力がこの3形式の
いずれとも異なる場合**（自作テストランナー・他言語のフレームワーク等）、書かないと
`count-skips.sh` が既定で `skips=unknown` になり、SKIP件数の検証が効かないまま run が進む。
該当する場合は Epic issue 本文に `## SKIPパターン` 節を**必ず書く**。

書式は SKIP行に一致する ERE（拡張正規表現）を1行だけ書く。

````markdown
## SKIPパターン

```
^  skip - 
```
````

節があれば run がその内容を `DEV_WORKFLOW_SKIP_PATTERN` として読み取り、Step 3 の各 generator
プロンプトと統合ゲートの両方に渡す（`## 準備コマンド` 節と同じ抽出方法）。書き方の詳細は
README「Epic の `## SKIPパターン` 節」を参照。Task issue 側にはこの節を書かない
（`## 準備コマンド` 節と同じく、Epic 側に1回書けば全タスクに効く）。

#### 編集時チェック（該当する場合のみ）

駆動先プロジェクトに型チェック単体・lint単体（**秒オーダーで終わるもの。テストスイートでは
ない**）のコマンドがあり、それを編集直後にPostToolUseフックで即座に差し戻したい場合、
Epic issue 本文に `## 編集時チェック` 節を書ける（任意。無くても run は現行どおり動く）。

書式は空白区切りで1行に「編集ファイルに一致させる glob」と「実行するコマンド（`{file}` が
編集ファイルパスに置換される）」を並べる。

````markdown
## 編集時チェック

```
*.go   test -z "$(gofmt -l {file})"
*.py   ruff check {file}
*.ts   npx tsc --noEmit -p tsconfig.json
```
````

**非0終了でのみ差し戻すため、違反を終了コードで表現できるコマンドを書くこと**
（`gofmt -l` のように違反ファイルを一覧に出すだけで終了コードが常に0のコマンドは、違反が
あっても永久にブロックしない。`test -z "$(gofmt -l {file})"` のように終了コードへ変換する）。

節があれば run が Epic 開始時にマーカーファイルへ書き出し、`scripts/edit-check.sh`
（PostToolUseフック）がそれを読んで動く。**このチェックはホスト側で実行される**ため、
ホストにツールチェインが無いプロジェクトでは効果が無い（該当する拡張子の行を書かなければ
何もしない。フェイルセーフ）。書き方の詳細は README「Epic の `## 編集時チェック` 節」・
`docs/adr/0005-edit-time-check-hook.md` を参照。Task issue 側にはこの節を書かない
（他の任意節と同じく、Epic 側に1回書けば全タスクに効く）。

#### Task issue の自己完結化

Task issue は、それ単体を読むだけで実装に着手できるように書く。Epic 本文（仕様書・計画書で
数百行になりうる）を毎回読み直させない。最低限、以下を Task issue 本文に含める。

- 実装に必要な仕様（Epic 仕様書の該当節の要約・引用）
- 対象ファイル
- 完了条件（テストを含む）
- 前提となる背景（なぜこの変更が必要か）

```bash
# Epic issue作成後にブランチ作成
git checkout main && git pull
git checkout -b "epic/epic[番号]/[機能名]"
git push -u origin "epic/epic[番号]/[機能名]"
```

### Phase 4: 確認依頼

成果物一覧を表示し、ユーザーに確認を求める:

```
══════════════════════════════════════════
  計画フェーズ完了

  Epic:     #[番号] - [タイトル]
  ブランチ: epic/epic[番号]/[機能名]
  Tasks:    [件数] 件
  仕様書・計画書: Epic issue本文に添付済み

  タスク一覧:
  #XX Task: [タスク1] (Phase 1)
  #XX Task: [タスク2] (Phase 1)
  #XX Task: [タスク3] (Phase 2)
  ...
══════════════════════════════════════════
```

## 行動原則

- コードベースを十分に調査してから計画する
- Phase間の依存関係を尊重する
- プロジェクトの指示ファイルに記載されたルールに従う
- 既存のモジュール・パッケージとの整合性を確認する
