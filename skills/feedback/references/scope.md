# 修正範囲の境界と分類基準

`skills/feedback/SKILL.md` から参照される。分類に迷ったときはここを読む。

## 1. 触ってよい場所・いけない場所

| 対象 | 可否 | 理由 |
|---|---|---|
| 台帳ディレクトリ配下（`observations.tsv` / `learnings.md` / `upstream/`） | 常に可 | ハーネス由来の作業領域であり、駆動先リポジトリの外にある |
| プロジェクトの `CLAUDE.md` | **承認があれば可** | プロジェクトの知識なのでコミットしてよい。ただし勝手に育てない |
| プロジェクトの `.claude/settings.local.json` | **承認があれば可** | gitignore 済みが前提。追跡されている場合は書かず、その旨を報告する |
| プロジェクトのドキュメント・テスト・コード | **承認があれば可** | 通常の変更と同じ扱い。フィードバックの副作用として黙って直さない |
| 駆動先の `.gitignore` | **不可** | 駆動先の共有ファイル。README「ハーネス非注入原則」 |
| `${CLAUDE_PLUGIN_ROOT}` 配下（プラグイン本体） | **不可** | プラグインを利用者環境で書き換えると、更新で失われ、他の利用者にも届かない。還流させる |
| 他プロジェクトの台帳（`feedback/<別repo>/`） | **不可** | 分析対象は実行中のプロジェクトに限る |

唯一の例外は、駆動先が dev-workflow リポジトリ自身のとき（`collect-feedback-signals.sh` の
`repo.is_dev_workflow=1`）。このときプラグイン本体＝プロジェクトのソースなので、
通常の修正対象として扱ってよく、還流も不要。

## 2. project か harness か

**判定の質問: 「同じ問題は、dev-workflow を使う別のプロジェクトでも起きるか？」**

- 起きる → `harness`
- このプロジェクトの構成・規約・コードベース固有 → `project`
- 判断できない → `project` に倒す。**harness 側の誤検知は他人の issue 欄を汚すため、こちらのほうが安い**

### harness の例

- `sandbox-exec.sh` がある OS / パス形状で失敗する
- ウェーブ分解が `- 前提:` の特定の書き方を取りこぼす
- 可読性ガードが特定の言語で誤検知する
- SKILL.md の手順どおりに実行すると詰まる（記述と実装の乖離）
- watchdog が停滞を検知できない条件がある
- role 別トークン消費が構造的に増える経路がある

### project の例

- このプロジェクトのテストコマンドが `make test` である
- 特定ディレクトリの変更には追加のマイグレーションが要る
- このリポジトリの CI が特定の lint を要求する
- ドメイン固有の命名規約
- このプロジェクトの Docker イメージに特定のツールが足りない

### どちらでもないもの（記録するだけ・昇格させない）

- 1回きりのネットワークエラー、GitHub の一時的な障害
- ユーザーが途中で方針を変えたことによる手戻り
- モデル出力のゆらぎで、次に同じ条件で再現するとは言えないもの

## 3. category の使い分け

| category | 対象 |
|---|---|
| `gate` | テスト・ビルド・可読性ガード・統合ゲート |
| `sandbox` | Docker イメージ / compose / 共有ディレクトリ / マウント |
| `permission` | 許可プロンプトによる中断、settings の不足 |
| `plan` | 仕様ヒアリング・issue 分割・依存宣言・ウェーブ分解 |
| `review` | evaluator のレビュー、指摘の質、review issue の扱い |
| `telemetry` | watchdog / heartbeat / トークン記録 / 通知 |
| `docs` | README・SKILL.md・役割定義の記述と実装の乖離 |
| `other` | 上記に当てはまらないもの |

## 4. severity の基準

| severity | 基準 |
|---|---|
| `high` | 自律動作が止まる、誤った成果物がマージ候補になる、データを失う |
| `medium` | 手戻りが発生する、コストが構造的に増える、人手の介入が要る |
| `low` | 表示・文言・軽微な非効率 |

**severity は「困った気持ち」ではなく結果で決める。** 根拠にできる事実（停止した、
やり直した、トークンが N 倍になった）が示せないものは `low` にする。

## 5. キーの付け方

- 小文字英数字とハイフンだけ（`gate-readability-false-positive` など）
- **現象を表す。原因の推測を入れない**（原因は観測を重ねてから分かる）
- 新しいキーを作る前に `feedback-ledger.sh list` で既存キーを見る。
  **表記ゆれで別キーになると、いつまでも閾値に達しない**
- Epic 番号やファイルパスをキーに含めない（別 Epic で再現したときに繋がらなくなる）
